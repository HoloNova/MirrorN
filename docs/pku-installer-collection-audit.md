## 结论

当前只有五个可见软件，不等于北大只支持五个生态。问题分三层：少数软件入口被固定登记、Apache 文件判断过度依赖 `bin/binary` 文件名、数据库查询把有文件的软件直接当成生态。应修复这三个环节，而不是仅恢复空页面，或重新抓取全部依赖库。

前三个例子不是全部漏采清单。追加文件级复核已发现 MacTeX、BasicTeX、Rtools 和 Kubernetes 的实际安装包，以及七个 Linux 发行版生态的系统安装镜像。此前的采集范围排除和不完整调查，不能继续作为“其它生态没有安装文件”的证据；也不能承诺北大 40 仓库都有同类安装下载。

### CTAN：发现此前完全没有接入的安装入口

覆盖组当前元数据证据：`https://mirrors.pku.edu.cn/files/ctan/systems/texlive/tlnet/`，包含：

- `install-tl-windows.exe`：Windows 网络安装器。
- `install-tl-unx.tar.gz`、`install-tl`：Unix 安装程序入口，平台和使用前提需要专门标注，不能仅按压缩后缀归为源码或预编译包。

只采集审核的安装入口，不下钻 `archive/` 和 `tlpkg/` 全量依赖。网络安装器仍会在用户电脑上下载后续组件，不宣传为已包含全部内容的离线包。暂不撰写教程正文。

镜像文件大小不是 SQLite 记录占用：十几 GiB 的 ISO 也只保存文件信息和 URL，不下载包体。排除 ISO 并不是解决此前数据库膨胀的有效手段，减少重复记录和全库采集才是。

这是修复范围建议和证据纠正，尚未改变现行采集白名单。40 仓库仍需逐项核对适用入口、安装用途、已采到／被过滤／尚未核实原因；不能把本表再次当成最终漏采总数。

## 当前实现的具体缺口

- `apps/server/src/db/catalog.ts:29` 的 `syncCatalog()` 接收但未使用 `taxonomy/siteResources`，只登记固定的 `SOFTWARE`。
- `catalog.ts:88` 用软件 `slug/name` 填生态字段；`listEcosystems()` 也直接从软件及下载连接查询，生态和软件未区分。
- `catalog.ts:153` 的 `HAVING COUNT(d.id)>0` 使所有未产出下载的软件不进入首页搜索。
- `apps/server/src/indexing/installers.ts:153` 的通用 Apache 正则强制文件名出现 `bin/binary`，不能识别上述真实样本。
- `installers.ts:276` 的软件归属判断与 Kafka 实际命名不兼容。
- 现有源码排除使用单词边界，下划线分隔的 `_src` 等形式存在漏挡风险；`fulldocs` 也不能靠单独的 `docs` 词匹配解决。放宽接受规则前先补负样本。
- 有内容但零识别被记为不可重试错误；空数组被记为可重试错误。应区分正常无候选、未知用途与网络/解析故障，不反复将正常叶子目录当作网络失败。

Apache 根的本次实际执行输出为 `265` 条总记录、`262` 个目录、`3` 个文件，登记了 `262` 个项目。原覆盖报告引用的 `263` 项目与此不一致，不能混用；动态数字不成为固定配置。

## 修复方案

### 1. 先守住用途判断，再修真实漏收

保留按软件审核的规则，加入当前目录、项目身份及版本目录上下文。Tomcat 的 `bin/` 是用途证据，但仍排除文档、辅助部署包和源码；Kafka 用自己的命名模式区分软件版本、Scala 版本和源码/文档。

不采用“所有 zip/tar 都收”或“文件名任意位置出现项目名就收”的兜底。先补源码、文档、调试、校验与辅助包的负样本，再扩大接受范围。文件名、版本和下载链接仍全部动态产生，不维护静态实际文件表。

### 2. 保留受控目录发现，避免一端过窄、一端无界

采集限定在审核根内，保留防循环、深度、限速、旧任务保护及完整更新机制。目录发现与文件识别分开；仅有未知子目录名称不能作为整个软件“不存在”的证明。

对已确认的软件布局采用发布目录入口或项目级规则。未审核的项目可以记录为待核对身份，但不据此证明可下载；也不因暂未适配直接抹去站点的生态关系。未知目录/文件的原因和有限样本进入采集诊断，不长期保存原始索引正文。

正常空目录或无候选单独记录，更新不覆盖有效下载；网络/格式故障仍按原队列策略重试。撤销旧文件仍需完整、可信的对应范围结果，不能以一次零识别作为删除依据。

### 3. 补接已核实的 TeX Live，按证据扩展其它入口

新增软件身份、CTAN 安装根和用途规则；版本从本轮目录标记动态取得。同一 URL 只存一次，多平台适用性准确表达，不能用 `any` 将 Unix 安装器错误映射到 Windows。

Rtools 和 MacTeX／BasicTeX 已在追加复核中取得当前文件级元数据证据，应纳入软件入口和用途规则的修复清单。R 本体 Windows ARM64 仍待核实，不与 Rtools 的 ARM64 安装包混淆。Julia 根当前表现为包服务器，不能宣称它已经提供 Julia 语言安装器。

纯依赖索引、数据集、源码、Android 专用资源不因数量目标混入普通安装查询。但不能继续整体排除所有 Linux 安装资源：追加证据表明系统 ISO 和具体软件 DEB 有真实安装用途。建议调整为审核的系统安装镜像＋具体软件安装包；不因开放 ISO/DEB/RPM 后缀恢复全量包采集，也不把特殊固件和未知归档自动归为新手入口。该范围调整尚未实施。

### 4. 恢复生态、软件和站点的真实关系

继续使用 SQLite，不换数据库、不复制采集批次。

- 已有审核的生态和北大仓库关系用于建立身份目录，而不是静态导入实际文件。
- 软件关联所属生态：Apache 软件项目不再每个都生成一个新的 Apache 生态；同一生态可包含多个软件和版本。
- 站点支持生态的关系独立于是否已经采到下载；软件的下载记录仍以站点、版本及 URL 关联。
- 查询分别表达“已收录”“已产出下载”“尚未确认”，不能把未采到文件等同于生态不存在，也不能将目录根作为下载按钮。
- 名称/生态/版本查询走小规模身份关系与现有下载索引。保留去重、短整数关联、失败保旧及暂存清理，不回到百万包扫描。

只做必要功能接线，继续教程占位，不重做 UI。修复后的人工验收覆盖生态搜索、站点生态列表、软件下载平台/版本选择及有效直链。

## 非 UI 验证与交付标准

1. 以本轮真实文件名作为解析夹具：Tomcat 安装器/运行包和 Kafka 预编译包被识别，源码、fulldocs、site-docs、deployer、校验文件不进入普通安装查询。
2. 验证 Kafka 的软件版本与 Scala 版本分离；明确目录证据的边界，不把同名源码目录内容当运行包。
3. 验证正常无候选保旧、不产生无意义的失败重试；失败、解析中断及旧任务仍不能覆盖有效数据。
4. 验证生态和软件分离、站点关系不依赖下载数；“可下载”结果必须确有数据库文件，未确认项不冒充下载。
5. 受限后台实测复核两条 Apache 失败路径修复后产出安装下载、CTAN 入口产生正确版本和适用系统；仅元数据，不下载安装包。
6. 逐仓库交付当前验证、历史资料、未确认及范围外原因；不将静态目录条目数或已登记软件数充当实际下载覆盖。

本轮尚未修改业务实现，未提交、未部署。后续实现按上述审核后的证据推进，不直接采用原始子代理报告中的全部建议。
