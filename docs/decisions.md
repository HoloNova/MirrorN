# 架构决策记录

本文件记录会影响后续实现的取舍和实测数据，避免以后重新讨论或写出相互矛盾的代码。

## 前端不打包 zod，数据校验放在构建前与 CI

**日期：** 2026-09-18
**状态：** 已实施

**背景。** `packages/shared` 用 zod 定义数据契约，`apps/web` 最初在模块加载时调用 `MirrorListSchema.parse()` / `EcosystemListSchema.parse()`。这段校验在浏览器里没有新增保护：被打进前端产物的 JSON 来自同一个提交，而 CI 已经用同一份 schema 校验过它。

**实测体积（本次构建，zod 3.25.76）：**

| 方案                 | 压缩后       |
| -------------------- | ------------ |
| `zod`（v3 经典 API） | 13.8 KB gzip |
| `zod/v4`             | 45.9 KB gzip |
| `zod/v4-mini`        | 6.3 KB gzip  |

zod v3 无法 tree-shaking：只用一个 `z.object({ a: z.string() })` 也是 13.8 KB。

**决定。** 前端只用类型（`import type`），不认识 schema。数据校验保留在 `scripts/validate-data.ts`（CLI/CI）和 `apps/server`（阶段 5 接入上游数据时）。

**实测结果。**

|                 | 变更前                    | 变更后                   |
| --------------- | ------------------------- | ------------------------ |
| 前端 JS         | 142.09 KB / 44.78 KB gzip | 86.26 KB / 32.09 KB gzip |
| Vite 处理模块数 | 28                        | 15                       |

产物中已确认不含 `ZodError`、`safeParse` 等 zod 标记；镜像地址数据本身仍在包内。

**代价与对策。**

1. `apps/web/src/lib/ecosystems.ts` 里存在一处显式类型断言，属于信任边界。JSON 模块的字符串字面量会被推断为 `string`，无法直接赋给 `official | university | commercial | community` 这类联合类型，所以断言无法避免。该文件顶部的注释说明了这条信任链。
2. 校验一旦被跳过，前端不会报错，只会渲染错误内容。因此 `build`、`build:web`、`dev:web`、`dev` 都先执行 `validate:data`；`validate:data` 在数据目录为空时也会失败。
3. 类型断言只覆盖字段结构，不覆盖语义。镜像地址是否真的服务该生态仍靠人工核对，记录在 `docs/upstream.md`。

**对后续阶段的影响。** 阶段 2 的命令生成器会被前端调用，因此它必须保持零运行时依赖：只使用类型和纯函数，不 import schema。如果 `packages/shared` 的入口同时导出 schema 和生成器，前端引入生成器时会连带把 zod 打进产物。届时应拆分子路径导出（如 `@mirrorn/shared/generators` 与 `@mirrorn/shared/schemas`），而不是把 zod 重新加回前端。

## shared 包按子路径导出：schema 与生成器分开

**日期：** 2026-09-18
**状态：** 已实施

**背景。** 阶段 2 的命令生成器要被前端调用，而 `@mirrorn/shared` 的入口同时导出 zod schema。前端一旦从入口导入生成器，整个入口模块图都会进入浏览器产物，zod 就会重新回到前端。

**决定。** 拆成两个子路径：`@mirrorn/shared`（schema、类型、数据集校验，供 CLI 与服务端使用）和 `@mirrorn/shared/generators`（零运行时依赖的纯函数，供前端使用）。生成器只用 `import type` 引用类型，返回值全是字符串和纯对象。

**验证方式。** 编译后检查 `packages/shared/dist/generators/*.js` 不含 zod 引用；前端构建产物中不含 `ZodError`、`safeParse` 等标记。新增任何会被前端调用的 shared 代码时，都要维持这条约束：需要同时导出 schema 和运行时函数时，拆子路径，而不是合并入口。

## 前端路由使用 hash 模式

**日期：** 2026-09-18
**状态：** 已实施

**决定。** `apps/web` 使用 `createWebHashHistory()`，链接形如 `/#/ecosystems/pip`。

**原因。** 阶段 6 要把前端作为纯静态产物托管（可放任意静态服务器、对象存储或本地文件），hash 模式不需要为每条路径配置 history fallback，也不会在刷新时 404。代价是 URL 里带 `#`，对当前场景不重要。

**如需改用 history 模式。** 必须同时交付托管侧的 fallback 规则并在 README 中写明；不要只改前端而不改部署说明。

## 搜索使用 Fuse.js，意图词写在代码里、身份别名写在数据里

**日期：** 2026-09-18
**状态：** 已实施

**决定。** 前端用 Fuse.js 在内存中做检索（实测 min+gzip 9.3 KB，前端产物从 50.07 KB gzip 增至 64.20 KB gzip，含新增的镜像别名数据与搜索代码）。区分两类关键词：

- **身份别名**（`python`、`pip`、`装python`、`tuna`、`淘宝源`）属于数据事实，写在 `data/` 里，社区 PR 直接扩充。因此 `Mirror` schema 增加了必需的 `aliases` 数组，与 `Ecosystem.aliases` 对称。
- **语言层面的意图词**（`换源`、`huanyuan`、`镜像`、`加速`）对所有生态都成立，不是某个生态的事实，因此作为常量写在 `apps/web/src/lib/search.ts`。这样新增生态不需要重复填写这些词。

多词查询按“每个词都要命中”合并得分，`阿里云 pip` 会缩小范围而不是放宽范围；结果上限 8 条。

**结果卡片必须可以点进下一步。** 镜像命中时不显示无法点击的说明卡，而是展开该镜像在当前数据中真正服务的生态，由用户选择；没有对应生态的镜像不进入索引。这一条是对 `MAIN.md` 中“换源总览”页面的替代：阶段 3 不新增只有标题、没有目标的页面，`换源` 作为意图词直接命中各个生态。

## 键盘与输入法：判定逻辑与渲染分离

**日期：** 2026-09-18
**状态：** 已实施

**背景。** 搜索需要支持 `/`、Ctrl/Cmd+K、上下键、Enter、Esc，并且在中日韩输入法组词期间不能把 Enter 当作确认。真实输入法无法在无头浏览器里可靠复现。

**决定。** 键盘判定抽成纯函数（`apps/web/src/lib/keys.ts` 的 `resolveSearchKey`、`shouldFocusSearch`、`isEditableElement`、`moveIndex`），组件只负责调用和渲染。单测覆盖 `isComposing`、在输入框内不劫持 `/`、以及边界循环；E2E 覆盖真实按键流程，并用 `compositionstart`/`compositionend` 事件序列模拟组词状态。真正依赖具体输入法行为的部分无法自动化验证，这一点在 E2E 文件里写明。

## 搜索结果排序：生态优先于镜像

**日期：** 2026-09-18
**状态：** 已实施

**背景。** 初版只按 Fuse 模糊得分排序，输入 `pip` 时首个结果是"PyPI 官方源"（镜像），回车只会展开生态入口而不会进入向导。生态名与镜像名共用了同一批关键词（镜像的索引词里包含它支持的生态名），因此得分无法区分用户意图。

**决定。** 排序键改为 `（类型：生态 0 / 镜像 1）→ 模糊得分 → id`。搜到生态名时用户最可能想配置该生态；而镜像品牌名（`tuna`、`腾讯云`、`淘宝源`）不会与生态名竞争，因此这条规则不会遮住镜像结果，镜像命中仍然留在列表中作为第二种入口。单测固定了 `pip` / `npm` / `pypi` 的首位结果和镜像品牌仍然可搜。

## 探针写在数据里，跨域方式不靠运行时试探

**日期：** 2026-09-19
**状态：** 已实施（阶段 4）

**决定。** `Mirror.probe` 增加 `id`（探针标识，全库唯一）和 `mode: 'cors' | 'no-cors'`，
`cacheBust` 保留为逐条审核的开关。跨域方式是**审核结论**，不在运行时“先试 cors，失败再退回 no-cors”：
那样每个不合规的目标都会多发一次请求，第二次的耗时还带着已经建连的偏差。核实证据（状态码、体积、
CORS 头、真实浏览器结果）记录在 `docs/probe-validation.md`。

**实测改变了两个原设想：**

1. npm registry 的 `robots.txt` 是被占用的包名（返回 7.4 KB 的包元数据），改用 `/-/ping`。
2. 清华的 `robots.txt` 加查询参数会返回 403，因此它的探针 `cacheBust` 必须为 `false`。

**校验增强。** 探针 ID 必须唯一；探针地址的主机必须是镜像主页的主机、与主页同一站点，
或该镜像在生态数据里已经声明过的仓库主机（npm 官方 registry 与它的主页不同域，属于这一条）。

## 缓存按探针签名判断，而不是按全局数据版本

**日期：** 2026-09-19
**状态：** 已实施（阶段 4）

**决定。** `localStorage` 里的结构是 `{ version, entries: [{ signature, result, expiresAt }] }`。
`version` 是存储格式版本（结构变化时递增，旧数据整体作废）；每条结果的 `signature` 由探针的
`id | mode | method | cacheBust | url` 拼成，与当前数据不一致就直接忽略并覆盖写。

**原因。** 用一个全局的“数据版本”会在任何一条无关记录改动时丢掉全部仍然有效的测量结果；
签名只让真正变化的那条探针失效。默认 TTL 15 分钟（可按缓存实例配置），
过期条目仍保留最多 24 小时用于 SWR 先展示再更新，超过就丢弃；最多保留 32 条。

**存储不可用。** 创建缓存时会试写一次，发现不可用（无痕模式、被禁用、配额异常）就退回内存。
写入失败时同样落到内存，读取时按探针 ID 合并存储与内存条目，避免一次写入失败让结果整体消失。

## 探测轮次：去重与取消的边界

**日期：** 2026-09-19
**状态：** 已实施（阶段 4）

**决定。** 调度器（`apps/web/src/lib/probeRound.ts`）里有两处容易互相矛盾的语义，按下面的边界实现：

- **同一探针的请求去重跨轮次生效**：新一轮开始时不重复发起已经在跑的探针，而是复用同一个请求。
  因此新一轮**不会**取消自己仍然需要的请求。
- **“新一轮取消旧任务”只针对新一轮不再需要的探针**，而且旧轮次的回调在这一刻失效：
  它的结果即使随后返回，也不会被当成当前结果（用 `isCurrent()` 判定，而不是靠完成顺序）。
- 排队中的探针在真正发请求前再检查一次取消状态，避免用户取消后仍然发出请求。

**并发上限是调度器级别的**：默认并发 3、每轮最多 6 个候选、单请求 1500 ms 熔断，
都来自 `PROBE_LIMITS`，可以在创建调度器时覆盖。

## 推荐评分：70/20/10 与“本轮”的解释

**日期：** 2026-09-19
**状态：** 已实施（阶段 4）

**决定。** 评分是纯函数（`apps/web/src/lib/recommend.ts`）：延迟分 `clamp(1 - durationMs / timeoutMs, 0, 1)`，
同步分 成功 1 / 同步中 0.5 / 未知 0.5 / 失败 0，稳定性项目前对所有来源取同一个中性值 0.5，
权重 0.7 / 0.2 / 0.1。阶段 4 没有上游同步数据，界面显示“未知”，不把缺失当成成功，
也不按高校或商业身份编造稳定性差异。

**参与自动推荐的条件**：有结果、`status === 'ok'`、不是过期结果、没有明确的同步失败。
**有效期内的缓存结果算证据**：SWR 的目的就是让缓存先渲染，它和本轮结果在 15 分钟内是同一批网络条件下的测量；
过期结果（正在后台更新）不参与推荐，但仍会显示并标注“可能已过期”。

**排序只影响推荐，不改变界面里来源列表的顺序**：列表在探测过程中跳动比“顺序最优”更糟。
平分按稳定 ID 排序，保证同样输入得到同样输出。文案不使用“保证最快”。

## 探测文案与状态口径

**日期：** 2026-09-19
**状态：** 已实施（阶段 4）

- 统一写“响应耗时（估算）”，不写延迟、RTT、TTFB 或下载速度。
- no-cors 的 opaque 结果显示“响应完成，内容未验证”；能读到状态码时显示 “响应完成，HTTP 200”；
  可读的 404/403 记为**探测失败**，不当作“很快的来源”。
- 超时与失败都提示“也可能是浏览器策略或网络原因”，不宣称站点宕机。
- 不按耗时区间给颜色分级：那需要在数据之外发明“多快算快”的阈值，当前没有依据。

## dev 脚本不因后端崩溃而结束前端

**日期：** 2026-09-19
**状态：** 已实施

**问题。** 根脚本原本是 `concurrently --kill-others-on-fail ... "web" "server"`。后端因为端口被占用而退出时，concurrently 会把 vite dev server 一起结束：浏览器侧什么都没有，表现是白屏，而终端里只有一段 Node 栈，看不出“页面为什么打不开”。

**决定。** 去掉 `--kill-others-on-fail`。前端是页面可用性的关键，后端崩了不该带走它；反过来 vite 因端口被占退出时会明确报错，留着一个后端进程也不影响判断。Ctrl+C 仍然会同时结束两者（已实测 `SIGINT` 会终止两个子进程）。

## 后端端口在 dev 下用 `--port` 固定，不继承通用 `PORT`

**日期：** 2026-09-19
**状态：** 已实施

**问题。** `apps/server` 原本按 `process.env.PORT ?? 8787` 取端口，而 `PORT` 是同机其他工具（Web 面板、代理等）会占用的通用变量。`pnpm dev` 继承 shell 环境后，后端会去绑那个被占用的端口并崩溃 —— 前面那条 `--kill-others-on-fail` 再把它放大成整站白屏。

**决定。** 端口解析顺序改为 `--port`（可重复，最后一个生效）→ `MIRRORN_PORT` → `PORT` → `8787`，dev 脚本显式写 `--port 8787`。这样：

- dev 端口与 shell 环境无关；需要换端口时 `pnpm --filter @mirrorn/server dev -- --port 9000` 即可（脚本里那个 `--port` 在前，后出现的生效）。
- 部署时平台注入的 `PORT` 仍然生效（那时没有 `--port`），项目专用变量 `MIRRORN_PORT` 优先于通用 `PORT`。
- 不再需要为了脚本里写环境变量而引入 `cross-env`（Windows 的 `cmd`/PowerShell 不支持 `VAR=value 命令` 这种前缀写法）。

端口被占用时不再抛裸栈，而是打印三行可照做的提示（查看占用者的命令、结束旧进程或换端口）并以退出码 1 结束。解析逻辑放在 `apps/server/src/config.ts`，是纯函数，有单测覆盖各种取值与优先级。

## vite 使用 `strictPort: true`

**日期：** 2026-09-19
**状态：** 已实施

**决定。** 端口 5173 被占用时直接失败，不再静默改用 5174。默认行为会让“终端里显示的端口”和“用户以为在看的页面”不一致：本次排障中就出现过一次 5173/5174 混淆，以及一次“服务其实整组退出、但页面地址看起来没变”的情况。静默降级把排查成本推给了用户，明确失败更便宜。e2e 用 `--port 5199 --strictPort`，与这条配置一致。

**副作用。** 同一时间只能跑一个 vite 实例；多个实例共用 `apps/web/node_modules/.vite` 预打包缓存，后启动的实例重建缓存（常见触发：改了 `vite.config.ts`、`packages/*/package.json` 或依赖）会让已打开页面加载失败，表现为白屏，重新加载即可。README 里已写明这条。

## 浏览器 API 差异不能让向导白屏：只把真正的 EventTarget 当事件源

**日期：** 2026-09-19
**状态：** 已实施（阶段 4 修复）

**问题。** `createBrowserProbeEnv()` 原本这样取网络状态源：

```ts
const connection = (navigator as Navigator & { connection?: EventTarget })?.connection;
connection?.addEventListener('change', onChange);
```

`?.` 只能挡住 `undefined`，挡不住“存在但接口不完整”。部分 WebView / 嵌入式浏览器会暴露
`navigator.connection` 却没有 `addEventListener`，于是这一行在 setup 阶段抛
`TypeError: connection?.addEventListener is not a function`：整个向导页渲染失败，页面一片空白，
而**终端没有任何报错**（报错只在浏览器控制台）。用仿真的部分实现复现过：向导页 `#app` 只剩 465 字符。

**决定。**

1. 新增 `asEventTarget()`：只有当 `addEventListener` 与 `removeEventListener` 都是函数时才把对象当事件源，
   否则直接忽略（`docs/decisions.md` 里这条适用于以后所有"可选浏览器 API"的接入）。
2. `subscribe()` 注册中途抛错时先撤回已经注册的监听器再抛出，避免留下没人清理的监听器。
3. 新增 `createMirrorProbeAccess()`：测速初始化失败时降级为"本次无法测量"，向导、命令与排错照常可用，
   失败原因打到控制台。组件改用这个入口，`useMirrorProbes()` 本身保持会抛错（便于测试与定位）。
4. 视图里区分 `unavailableReason`：`no-probe`（数据里没有探针）与 `probing-disabled`（本次测速不可用）。
   降级时显示"本次无法测量 · 测速初始化失败，原因见浏览器控制台；向导本身仍然可用"，
   不把"初始化失败"误报成"数据里没有探针"。
5. `runProbe()` 里取消响应正文也做了防御：`body` 或 `cancel` 不标准时忽略，不让一次成功的响应被判成失败
   （耗时在取消之前就已经算完，所以也不改变测量值）。

**验证。** 仿真"`navigator.connection` 是普通对象"时向导页完整渲染（7388 字符，与正常一致，控制台无报错）；
仿真"注册网络监听抛错"时页面同样完整（10594 字符），三个来源显示"本次无法测量"，命令照常生成；
`apps/web` 单测 111 条通过，含以上两条路径。真实浏览器上仍无法枚举所有 WebView 实现，
因此这条修复的价值是"接口不完整时降级而不是白屏"，而不是"断言这些浏览器一定正常"。

## 端口预检与 e2e 缓存隔离：一个"启动失败也会破坏现场"的坑

**日期：** 2026-09-19
**状态：** 已实施（排障后补的防护）

**现象。** 页面白屏或标签页一直转圈（Network 里请求 pending），而**终端毫无报错**。当天出现了三次。

**机制。** Vite 的依赖预打包（`node_modules/.vite/deps/`）发生在**绑定 HTTP 端口之前**。所以在同一仓库里再启动一个 vite 实例时：

1. 新实例先重建共享的 dep 缓存（会先删掉旧文件）；
2. 新实例随后绑定端口失败退出（`strictPort` 下必然失败，我当天正是如此）；
3. 但**已经在运行的**那个 dev server 的模块图仍指向刚被删掉的文件，于是浏览器请求依赖时拿到 **504（Outdated Optimize Dep）**；
4. Vite 客户端检测到 504 后发起整页重载，重载后依旧拿不到依赖 —— 无限重载，界面上就是白屏或一直 pending。

**证据。** 第二次启动后 `apps/web/node_modules/.vite/deps/` 整个消失（连 `_metadata.json` 都没有）；服务端模块里引用的 `/node_modules/.vite/deps/vue.js?v=8c922ec6` 返回 504；重建之后同一个 URL 返回 200，页面恢复正常。

**决定。**

1. **dev 系列脚本先做端口预检**（`scripts/require-free-port.mjs`）：5173 / 8787 被占用时立即退出，**在碰任何缓存之前**失败，并打印占用者查询命令。这一步必须排在依赖预打包之前，否则防护没有意义。
2. **e2e 使用独立缓存目录**：`vite --mode e2e` 时 `cacheDir` 换成 `node_modules/.vite-e2e`。这样跑 e2e（或任何自动化）都不会影响正在浏览的 dev 页面，反之亦然。
3. **前端端口可用 `MIRRORN_WEB_PORT` 覆盖**（默认 5173，预检脚本跟着检查同一个端口）。保留这个开关是因为“某个端口打不开”可能来自我们代码之外的因素：VS Code 的端口转发条目、本机已有进程占用该端口、浏览器按 origin 缓存的 Service Worker（`localhost:5173` 与 `127.0.0.1:5173` 是不同 origin）。这种情况下换端口是最快的判别手段，从代码层面无法代修。后端同理可用 `--port` 覆盖。
4. **排查顺序写进 README**：这类故障要看浏览器 Console 与 Network，而不是终端；依赖文件 504 就是"缓存被另一个实例重建过"，重启 dev server 即可恢复；只某个端口不行时，按主机名写法、无痕窗口、Simple Browser、VS Code Ports 面板、本机占用顺序排查。

**为什么不是只写文档。** 三次故障里有三次都是"启动第二个实例"引起的，而人对"再开一个窗口试试"的直觉非常强；把检查做进脚本比依赖记忆可靠。仍然无法自动挡住的只剩"先 Ctrl+C、再启动"这种正常流程。

## 公开部署：静态产物交给已有的 Caddy，不反代开发服务器

**日期：** 2026-09-19
**状态：** 已实施（已上线 <https://mirror.campuslink.vip/>）

**背景。** 这台 VPS 上 Caddy v2.11.4 已在 80/443 服务 `pi.campuslink.vip`（Authelia + pi-web），Let's Encrypt 自动签发在该主机已验证可用，`mirror.campuslink.vip` 的 DNS 也已指向本机。

**决定。**

1. **静态托管，不用反向代理**：Caddy 用 `file_server` 直接读 `/srv/mirror.campuslink.vip/current`。前端是纯静态站点（hash 路由，服务端只会收到 `/`，不需要 `try_files`），不需要任何常驻 Node 进程。开发端口 5173/5174/8787 始终只绑 `127.0.0.1`，不对外暴露，也不被 Caddy 代理。
2. **部署要复制产物，不能让 Web 服务器读仓库**：仓库在 `/root` 下，`caddy` 用户读不到；而且让线上读工作区会把部署与开发耦合。`scripts/deploy-static.sh` 负责 `pnpm build:web` → rsync 到 `current/`，并留硬链接快照 `releases/<时间戳>`（保留 5 份）供回滚。
3. **缓存策略按内容可变性划分**：`/assets/*` 一年 immutable（文件名带内容 hash），`index.html` `no-cache`（否则新版本发布后用户一直拿旧引用），favicon 一天。
4. **后端暂不对外**：`/api` 只有健康检查，暴露没有收益只增加攻击面。阶段 5 接入 MirrorZ 后再在同域加 `reverse_proxy 127.0.0.1:8787`。
5. **启用 `encode zstd gzip`**：与 pi 站点不同（那边因 SSE 的 `text/event-stream` 会被 encode 的默认 Content-Type 匹配破坏而刻意关闭），本站点全是静态文件。
6. **校验必须以 caddy 用户执行**：`caddy validate` 作为 root 运行会预建 root 属主的 `/var/log/caddy/*.log`，导致 caddy 无法启动。这条来自 pi 站点的维护记录，本次已避开（先用 /tmp 日志路径校验片段，改完再用 caddy 用户校验整份配置后 `systemctl reload`）。

**证据。** `curl -I https://mirror.campuslink.vip/` → HTTP/2 200，`cache-control: no-cache`；`/assets/*.js` → `public, max-age=31536000, immutable`；证书 `CN = mirror.campuslink.vip`（Let's Encrypt，2026-09-19 → 12-18 自动续期）；访问日志里出现外部爬虫请求（`209.38.111.38`），证明公网可达；`pi.campuslink.vip` reload 后仍 302 → Authelia。完整步骤见 `docs/deployment.md`。

## 不把 CERNET 的选源评分配置成推荐输入

**日期：** 2026-09-19
**状态：** 已核实并放弃

`https://mirrors.cernet.edu.cn/api/scoring` 是 MirrorZ 302 重定向服务的评分接口（字段 `pos/mask/geo/isp/delta/unknown/abbr/label/resolve/repo`），它按**请求来源 IP** 计算网络距离。

**不用的原因**：那是服务端视角的网络评分。若由我们的后端去请求，得到的是**我们机房**（德国）到各镜像站的距离，与访问者浏览器到镜像站的路径无关；把它当推荐输入会系统地误导用户。这与阶段 4 已记录的结论一致（出口指纹只反映服务端出口）。该接口仅作为后续可能的地理定位参考记录在 `docs/upstream.md`。

## 同步状态：作用域、数据声明与“过期即未知”

**日期：** 2026-09-19
**状态：** 已实施（阶段 5）

**背景。** 上游核实结果是只有清华 pip 发布了机器可读的同步状态（`static/tunasync.json`，182 条作业），其余来源没有可核实接口（细节见 `docs/upstream.md`）。

**决定。**

1. **作用域是“镜像 × 生态”，但声明分两级**：站点级的状态文件地址写在镜像的 `statusSource`，镜像×生态对应的作业名写在 `MirrorSupport.statusJob`。理由：上游文件是按站点发布的（一个 URL），作业是按仓库组织的（一个 name），分级声明正好对应这两个事实；接口输出仍然是每对 (mirrorId, ecosystemId) 一条记录（PLAN 要求不能被站点总状态代替）。校验器额外保证：状态文件必须属于镜像自己的站点、没有 `statusSource` 不能写 `statusJob`、同一作业名不能被两条支持记录占用。
2. **过期即未知。** 超过 `SYNC_STALE_AFTER_MS`（默认 45 分钟 = 三次同步周期）未成功更新时，接口把所有 status 上报成 `unknown`，同时返回 `stale: true` 与 `lastSuccessAt`。理由：PLAN 明确要求“无数据或过期数据标记未知，不能伪装为实时状态”；保留时间戳是为了让界面能说“最近一次成功在 3 小时前”，这比一句“未知”更有用，也不会误导。
3. **`paused` 与 `failed` 都不参与自动推荐。** 上游有 4 种真实状态（success/syncing/failed/paused），PLAN 只规定了 4 档分数（成功/同步中/未知/失败）。我们的处理：分数上 paused 与 failed 同为 0（内容都没在更新），并且两者都排除出自动推荐，但用户仍可手动选择。理由：暂停同步的镜像对“想装包的人”和同步失败几乎等价，而推荐位是默认选择，宁可不选。
4. **官方源不加分。** 官方入口没有同步概念，界面显示“官方源”，评分保持中性的 0.5。理由：给它 1.0 等于用权重替用户决定“用官方源”，那是产品决策而不是数据事实。

## 网络指纹：前缀粒度与转发头取值

**日期：** 2026-09-19
**状态：** 已实施（阶段 5.4）

1. **粒度**：IPv4 取 /24、IPv6 取 /48 后做 HMAC-SHA256，截断 16 位十六进制。理由：同一出口（家庭/机房 NAT）应得到同一指纹，而 /32 会把它变成个人标识；/16 又会让不同校园出口混为一谈。
2. **`X-Forwarded-For` 取最后一个地址**，且只在 `MIRRORN_TRUSTED_PROXY=true` 时解析。理由：可信代理（本机 Caddy）把真实客户端地址追加在末尾；如果取最左边，客户端自己先塞一个 `X-Forwarded-For: 1.2.3.4` 就能伪造指纹。默认 `false` 表示“不知道前面有没有代理”，此时只用 socket 地址。
3. **拿不到可信地址就返回 `available: false`**，不用代理地址凑一个假指纹；前端据此退回阶段 4 策略（网络变化监听 + 手动刷新）。
4. 接口 `Cache-Control: no-store`，不记录原始 IP，也不声称完全匿名（同网段用户共享同一指纹，这是设计目标）。

## 后端部署：单文件打包 + systemd（非 root），生产端口 8788

**日期：** 2026-09-19
**状态：** 已实施

1. **单文件打包（esbuild）**：`pnpm --filter @mirrorn/server build:bundle` 产出 `dist/server.js`（230 KB，无外部依赖），部署时只复制它和 `data/`。理由：不需要把 `node_modules` 搬进 `/srv`，也不需要让服务以 root 读仓库（仓库在 `/root` 下，非 root 用户根本读不到）。
2. **非 root 运行**：专用系统用户 `mirrorn`，单元里开 `ProtectSystem=strict` / `ProtectHome` / `NoNewPrivileges` 等，只用 `ReadWritePaths=/var/lib/mirrorn` 放行快照目录。
3. **生产端口 8788，dev 端口 8787**：dev 工作流把 8787 固定给开发后端（见 README），生产服务用 8788，两者可同时运行、不会互相抢占。部署脚本会在重启前检查端口占用者并直接失败，因为“端口被别人占着”时 `curl /api/health` 仍然会返回 200——部署脚本曾经因此误判成功。
4. **两个实测坑已写进部署脚本**：
   - 系统 `/usr/bin/node` 可能是 v12，跑打包产物直接 SIGILL；脚本先校验 `Node >= 20`（本机用 `/usr/local/bin/node`）。
   - systemd 的 `MemoryDenyWriteExecute=yes` 会让 V8 在启动时 `V8_Fatal`（`OS::SetPermissions` / `Check failed: 12 == errno`），因为 JIT 需要可写可执行内存。因此单元里**刻意不开**这一项。

## 阶段 6：apt 与 Docker 的内容范围

**日期：** 2026-09-19
**状态：** 已实施

1. **apt 只覆盖 Ubuntu LTS 20.04 / 22.04 / 24.04，且只覆盖 amd64。** 其他发行版的仓库结构完全不同，套用会得到 404 或装错包；arm64/armhf/ppc64el 等架构在 `ubuntu-ports`（地址与目录都不同）。因此数据里**没有**这些组合，界面不会给出可选项，前置条件与排错卡片里给出 `lsb_release -ds`、`dpkg --print-architecture` 的自检方法以及 ubuntu-ports 帮助页入口。宁可少给，也不给一份可能在别人机器上出错的配置。
2. **安全更新（-security）保持官方源。** 生成的配置里归档与 `-updates/-backports` 走镜像，`-security` 仍指向 `security.ubuntu.com`：这是清华镜像帮助页的默认建议，理由是镜像同步有延迟而安全更新怕延迟。想要全走镜像的用户可以用配置文件内容里的注释行自行替换（界面上写明了不推荐）。
3. **配置格式按版本走，而不是让用户再选一次格式。** 24.04 默认就是 deb822（`/etc/apt/sources.list.d/ubuntu.sources`），22.04/20.04 默认是 `sources.list`。多一个“格式”维度会让选择器变成两轴组合，而这两者本来就被 Ubuntu 版本绑定。
4. **“持久化”用定向 sed 而不是整份覆盖。** 只替换归档行（deb822 只动第一个 `URIs:`；sources.list 跳过带 `-security` 的行），保留用户自己加的行与注释，并在命令里先做 `cp -a` 备份。配置文件内容仍然完整给出，供喜欢手工编辑的人使用。
5. **Docker CE 与 Docker Hub 加速是两个生态。** `docker-ce` 换的是 apt 软件仓库（安装/升级 docker-ce 用的包），`dockerhub` 改的是 `daemon.json` 的 `registry-mirrors`（拉取镜像用的加速）。两者混在一起是常见误解（清华的 docker-ce 页面也专门强调“本镜像不是 Docker Hub”），所以界面上分别成项，各自的前置条件第一条就说清区别。
6. **dockerhub 不内置任何加速地址。** 公共加速地址频繁变更、部分只缓存部分镜像，且我们无法核实其长期可用性与可信度——写进去就等于替用户承担风险。指南提供的是：`daemon.json` 的合并方式（保留其它键）、依赖检查（没有 python3 时明确失败、不写坏文件）、验证命令与还原命令，地址留成 `<你的加速地址>` 由用户自己填。
7. **容器部署用单镜像（同一个进程提供 `/api` 与静态页面）。** 目的是“一个端口、一个数据卷、回滚即换镜像”；生产站点仍然是 Caddy + systemd（`file_server` 直接读磁盘）。两条路径共用同一份数据与构建配置，差别只在部署方式。
8. **`MemoryDenyWriteExecute` 在容器镜像里不需要担心，但在 systemd 单元里必须关掉**（V8 的 JIT 需要可写可执行内存，否则启动即 `V8_Fatal`）。这条在阶段 5 部署时踩过，容器镜像里没有开这一项，systemd 单元里也留了注释说明为什么不开。

## 阶段 6：按版本区分的模板如何选择

**日期：** 2026-09-19
**状态：** 已实施

**背景。** 同一个「系统 + 终端」组合下，apt 的命令会因为发行版版本不同而不同（仓库代号、配置文件格式）。原来的生成器只按 `os + shell` 过滤，遇到多个候选就直接报“需要先确定具体系统版本”，但界面上没有地方能确定版本。

**决定。** 把 `version` 提升为**数据驱动的一等维度**，而不是在代码里写死“Ubuntu 版本列表”：

1. 数据里给模板加 `distribution` + `version`（`GuideVariantSchema` 本来就有这两个可选字段，无需改契约）；`listPlatforms` 额外返回该平台声明过的版本列表，顺序就是数据里的顺序（按新到旧排列）。
2. 向导新增“发行版版本”选择器，**只在数据声明了版本时出现**；默认取第一个（最新），切换系统时若该系统没有版本维度就清空。
3. 生成时把版本传给 `generateGuide`：数据不按版本区分时忽略该参数（兼容 pip/npm 现有行为），按版本区分但没有传版本时报 `ambiguous-platform` 并列出可用版本，传了数据里没有的版本时报 `unsupported-platform`。
4. 校验新增三条数据质量规则：同一「系统 + 终端」下不能混用带版本与不带版本的模板（否则不带版本的那个永远选不到）；同一版本只能有一个模板；声明了 `version` 就必须声明 `distribution`（否则界面只能说“24.04”，说不清是什么的 24.04）。

## 界面行为改为人工验收（不再维护 E2E 套件）

**日期：** 2026-09-19
**状态：** 已实施

**决定。** 删除 `e2e/` 下的 Playwright 用例、`playwright.config.ts`、`@playwright/test` 依赖与
`pnpm test:e2e`，CI 的质量门禁只保留格式、lint、类型、数据校验、单测与构建。界面行为改由人工在浏览器里按
`docs/acceptance-checklist.md` 核对。

**原因。** 界面验收是**判断**，不是断言：配色是否耐看、命令读起来是否顺、中文行长是否舒服、移动端参数条
会不会吃掉太多视口——这些没有可断言的正确值，写进用例只能固化成"当前实现长这样"，改设计时还要连着改测试。
真正需要断言的部分（命令生成、参数联动、推荐与同步状态评分、进度存取）都已经抽成不依赖 DOM 的纯函数，
留在单测里；而把浏览器流程也自动化的代价是：每次改界面都要跟着改一遍选择器与断言，维护成本落在改动最多的
那一层。用户明确要求"界面由我自己在浏览器里验收"，这条决定与之一致。

**代价（明确记录）。** 最容易出的三类回归不再有自动拦截，改为人工核对：

1. 主题三处（注册表 / CSS 选择器 / `index.html` 首屏脚本）不一致 —— 表现为切换无效或首屏闪白；
2. 参数联动漏改 —— 某个系统/终端组合下命令没有同步改写；
3. 降级路径失效 —— `/api` 不可用时报错而不是显示"同步状态未知"。
   这三条已列在 `docs/acceptance-checklist.md` 第 2 节。

**恢复方式。** 这些用例在 git 历史里（删除前最后一次提交），需要时可从当时的
`e2e/`、`playwright.config.ts` 与 `package.json` 里取回。

## 测速改为每个来源多次尝试、取最快两次平均

**日期：** 2026-09-21
**状态：** 已实施

**背景。** 实测与用户反馈一致：同一次访问里第一次测量偏高，再点一次就低下来。原因是测量口径本身——
`performance.now()` 包住的是整个 `fetch()`，第一个请求里包含 DNS 解析、TCP 握手与 TLS 握手，第二个请求
复用了连接池里的同一条连接。而跨域资源在没有 `Timing-Allow-Origin` 时，Resource Timing 的
`domainLookupStart` / `connectStart` / `secureConnectionStart` / `requestStart` / `responseStart` 会被
浏览器置 0（`nextHopProtocol` 也是空串），事后**无法把建连时间扣掉**。第一轮还常常与页面挂载渲染同时发生，
主线程忙会推迟 `await` 的恢复，数字再被抬高一点。

**决定。** 每个候选占**一个**并发名额，在名额内连续尝试 `PROBE_LIMITS.attemptsPerTarget = 3` 次，取
**最快两次的平均**；聚合规则集中在 `apps/web/src/lib/probeAggregate.ts`（纯函数，有单测），结果里带
`attempts` / `samples` 两个可选字段，样本不足时界面如实说明（"3 次尝试中只有 1 次拿到数值"）。
停手条件有两个：达到计划次数，或连续失败 `PROBE_CONSECUTIVE_FAILURE_LIMIT = 2` 次（避免对一个不可达的
来源白等三倍超时预算）。一次都没拿到数值时：全部超时记 `timeout`，否则记 `failed` 并保留状态码。

**被否的两个方案。**

1. **页面加载即预连接（`<link rel="preconnect">`）或预热一轮。** 浏览器对未被使用的预连接关得很快
   （Chrome 的 Lighthouse 文档与 Akamai 的实测都写约 10 秒；Chromium 里空闲 socket 的存活上限也在
   60 秒这一档），用户看完说明再点测量时连接通常已经关掉，第一轮仍然是冷的。而且它会在用户点击之前就向
   6 个第三方主机建连，直接违反首页与验收清单第 3 项"未点击时网络面板无第三方请求"。
2. **把并发从 3 提到 9，让同一候选的三次尝试并行。** 对镜像站的瞬时压力随尝试次数放大，几个建连之间还会
   互抢带宽与 CPU，测出来的值更不代表真实链路。占一个名额、串行尝试既保持了"任何时刻最多 3 个来源在测"，
   也让第二次起确实复用同一条连接。

**代价（明确记录）。** 探针请求数变成 3 倍（每轮 6 → 18 发，全部是 2 B–4 KB 的小资源），一轮耗时约 3 倍，
最坏情况（来源连续两次超时）单个来源 3 秒。因此界面文案按常量改写为"每个来源连续测 3 次，通常 1–3 秒出结果
（有来源超时会更久）"，不再写"约 1–2 秒"。评分与排序逻辑不变：一轮仍然只产生一条聚合结果。

**验证。** `probeAggregate.test.ts` 覆盖取值规则（三次取最快两次、两次取平均、一次标注样本数、全失败、
取消优先、opaque/状态码取自最快样本）；`probeRound.test.ts` 覆盖尝试次数、连续失败提前停止、尝试次数配成 1、
以及"总并发与尝试次数无关"。真实浏览器下的冷/热差异属于人工核对项，见 `docs/acceptance-checklist.md`。

## 界面文案口径（本轮措辞调整）

**日期：** 2026-09-21
**状态：** 已实施

对照《优化方案与文案规范》逐条评估后，采用它的**语气**（紧凑、术语化、数字化序列），但不采用与本项目已定
规则冲突的写法。具体口径：

5. **顶栏数据模式**改称「本地数据」/「同步状态在线」；搜索框占位符改「检索生态、工具链或系统...」，
   `/` 提示保留。
6. `GUIDE_MODE_LABELS`（`@mirrorn/shared/generators`）改为 **瞬态执行 / 持久写入 / 配置文件**，三处界面与
   单测同步改写。

## 改动对照（Config Diff）只对 apt 与 docker-ce 显示

**日期：** 2026-09-21
**状态：** 已实施

**决定。** 第 02 节的"配置文件"下面增加一张对照卡：同一份配置用**同一个生成器**渲染两次（一次用数据里的
官方来源地址、一次用当前选中的镜像），逐行比对，只列出真正变化的行（`-` 官方默认、`+` 换成镜像），没列出的
行就是不会变的行。差异计算在 `apps/web/src/lib/configDiff.ts`（纯函数 + 测试），是否显示由
`apps/web/src/lib/configBaseline.ts` 的 `CONFIG_DIFF_ECOSYSTEMS = ['apt', 'docker-ce']` 决定。

**原因。** 价值取决于"配置文件里有多少行**不该**动"。apt 的文件里除了仓库地址还有 `Signed-By`、安全更新
段落（保持 `security.ubuntu.com`）和注释；docker-ce 同样只改 `URIs:` 一行。用户最不放心的正是这几件事：
我自己加的行会不会被覆盖、安全更新那几行动没动。pip / npm 的配置基本只有一行 `index-url = …`，对照等于把
上面那份文件再写一遍；dockerhub 更是**没有配置文件**（它改的是 `daemon.json` 里的一个键，加速地址由用户
自己填，数据里也没有第二个来源可作基线），因此三者都不显示这张卡。

**注释行的变化单独计数。** 样本里带 `{{mirrorUrl}}` 的示例注释（例如"确实要让安全更新也走镜像时……"）会
跟着镜像一起更新，但它们不影响生效配置。汇总句因此写成"共 16 行，3 行生效配置会改，另有 3 行注释里的示例
地址跟着更新，其余 10 行不动"，全部变化都在注释里时直接说明"生效配置没有任何变化"。

**边界（必须写在卡片上）。** 对照的"改动前"是**官方默认配置**，不是用户机器上现在的文件——浏览器读不到本机
文件，也没有读取过其中的内容。这张卡不是红绿配色：颜色在这套设计里只表达语义（成功 / 同步中 / 失败），
"这一行会被替换"用结构色与面层深浅区分（`+` 是要生效的值、`-` 是下沉的旧值）。

## 不做独立的"网络遥测卡片"

**日期：** 2026-09-21
**状态：** 已决定（不实现）

《优化方案》2.1 建议在搜索框下方放一张卡片，展示"出口网络: CERNET"、"协议: HTTP/3 (QUIC)"、
"本地接入: 华东"、"节点并发探活: 12 Nodes"。逐项对照可得性后**不实现**：

| 想展示的字段          | 实际情况                                                                                                               |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `协议: HTTP/3 (QUIC)` | `PerformanceResourceTiming.nextHopProtocol` 需要响应带 `Timing-Allow-Origin`，否则为空串；我们测的都是第三方镜像站     |
| `出口网络: CERNET`    | 后端 `/api/net-fingerprint` 只返回网段 HMAC（`{ available, fingerprint }`），没有 ISP/ASN 信息，要做就得引入 IP 地理库 |
| `本地接入: 华东`      | 同上，且这是对用户位置的推断，误差与隐私代价都不小                                                                     |
| `12 Nodes Active`     | 探针上限是 6 个候选、并发 3（`PROBE_LIMITS`），写 12 与事实不符                                                        |
| 连接类型              | 只有 Chromium 有 `navigator.connection`，Firefox/Safari 没有；只能作为可选行，不能当固定栏目                           |

**替代做法。** 首页测量区内增加一行**真实可得**的参数说明："N 个候选来源 · 同时最多 3 个 · 每源 3 次 ·
显示最快 2 次的平均值"，由常量直接渲染（改了参数却忘了改文案是最常见的漂移）。出口指纹仍然只用于
"换了网络就作废旧测量"这个内部判断，不在界面上展示成地理位置。

## 页面拆成「首页 / 站点 / 帮助」，侧边栏只在其中出现

**日期：** 2026-09-21
**状态：** 已实施

**决定。** 外壳从"单页 + 文档页"改成两种形态，由 `apps/web/src/router.ts` 的 `meta.layout` 决定：

| 形态  | 页面             | 结构                                                                    |
| ----- | ---------------- | ----------------------------------------------------------------------- |
| `app` | 首页、站点、帮助 | 左侧常驻导航（品牌 + 三个模块 + 数据模式 + 主题切换），内容独占右侧一列 |
| `doc` | 生态文档、404    | 没有全局侧边栏，品牌与设置回到顶栏                                      |

首页只留标题、搜索框与一行「测量我的网络」，**删除生态目录账本**；测量结果默认收起，点按钮才展开；帮助先留空壳（说明暂时从哪里取帮助 + MirrorZ 帮助文档外链）。

**原因。** 首页原来同时承担导航（账本）、测量与搜索三件事，而账本能起的作用已经被搜索覆盖，却占着首屏最大的一块。用户的要求是"本来就一个搜索框就行了"。搜索框留在首页而不是照 MirrorZ 放进「列表」页，是因为我们的搜索同时索引生态、镜像站与别名，它就是主路径。

**为什么生态文档页不挂全局侧边栏。** 文档自己有 208px 的页内目录栏，再加一列全局导航后内容区只剩 664px，小于 `--measure-wide` 780px（命令块宽度上限），命令会被压窄或出现横向滚动。数值与推导写在 `apps/web/src/styles/shell.css` 顶部的注释里。

**代价（明确记录）。** 文档页的返回路径依赖顶栏品牌与页内面包屑（没有侧边栏可点）；窄屏（≤900px）侧边栏折叠成顶部横向条，间距与高亮需要人工核对（见 `docs/acceptance-checklist.md` 第 1 节第 9 项）。

## 「站点」先用自己的数据，逐站适配上游；不复制 MirrorZ 的数据

**日期：** 2026-09-21
**状态：** 已实施（第一批）

**背景（2026-09-21 实测，不是推测）。** 需求是"把所有的镜像都拿过来"。核对结果：

- MirrorZ **没有公开的站点数据接口**：`mirrorz.org` 与 `mirrors.cernet.edu.cn` 上的 `/static/json/*.json`、`/mirrorz.json`、`/.well-known/mirrorz.json`、`/api/mirrors`、`/api/site` **全部 404**；它的前端数据在构建时由 `mirrorz-config`（**无 LICENSE 文件**）抓取后打包进 bundle。
- 各参与站的 `/mirrorz.json` 与 `/.well-known/mirrorz.json` 实测 6 个站点（USTC / BFSU / ZJU / SJTUG / NJU / HIT）**全部 404**。
- `https://mirrors.cernet.edu.cn/api/scoring` 能给出 **16 个参与 302 的站点**（`abbr` + `resolve`）但没有仓库清单，且**没有 CORS 头**（只能后端抓）；它的 `geo`/`isp` 字段对我们是无效数据（实测服务器在 Frankfurt，16 条全部 `unknown`、`geo=1e+100`）。
- 站点自己的状态文件：`/static/tunasync.json` 实测**清华 200（74 KB）、北外 200（38 KB）** 可用，USTC / ZJU / JLU / NJU / PKU / HIT / SJTUG / 阿里云 / 腾讯云全部 404；`/static/status.json`、`/static/mirrors.json`、`/static/js/options.json`、`/api/mirrors` 在另外 8 个站点上全 404。

**决定。**

1. 「站点」页这一版只用 `data/mirrors.json` 与各生态 `supports`：站点名、类别、主页、覆盖的生态与仓库地址，以及**声明了作业映射**（`statusJob`）的同步状态。没收录的字段（仓库清单、logo、存储用量、联系方式）不显示也不编造。
2. 仓库清单**逐站适配**：只有站点自己发布了机器可读数据才接。当前可接的是 tunasync 类站点（`/static/tunasync.json` + `/static/js/options.json` + `/static/status/isoinfo.json`），第一批为清华与北外。
3. 站点写成数据文件（后续新增 `data/sites/*.json`），**新增一个站点是纯数据改动，不动代码**。

**明确不做。** 不复制 `mirrorz-config` / `mirrorz-json-site` / `mirrorz-publish` 的代码或数据（上游无许可证，见 `docs/licenses.md` 与 `docs/upstream.md`）；不把 `/api/scoring` 接进推荐（阶段 4 已否决，本次实测再次确认它对我们是无效数据）。

**可并行的省事路径。** `mirrorz-schema`（数据格式）已经是 CC-BY-4.0，但数据仓没有许可。可以向 mirrorz-org 提议给数据加许可或提供公开接口；能成则少维护一批适配器，但**不作为计划前提**，A 路线的适配器照做。

## 宽度跟随视口；页脚删除；帮助页用自写的 Markdown 渲染

## 站点页是静态目录，不放同步状态与延迟读数

**日期：** 2026-09-21
**状态：** 已实施

**决定。** 站点目录（`/#/sites`）与站点详情（`/#/sites/:id`）只放静态信息：

- 目录行：站点名（可点进详情）、性质标签（官方 / 高校 / 商业 / 社区）、官方地址、覆盖生态数（由数据算出来）。
- 详情页：官方地址、覆盖生态数、探针地址（声明了探针才有）、状态文件地址（声明了状态源才有）、数据核对日期、核对来源列表。

**不放**同步状态，**不做**延迟测量，也不列出"该站点覆盖了哪些生态"的清单。

**原因。** 三个理由，都是内容性质而不是美观问题：其一，同步状态是按生态（上游作业）分开的，同一个站点在 `pip` 上有作业、在 `apt` 上没有，站点页只能挑一条显示，等于把"没有这个映射"和"数据没拿到"混成一团；其二，延迟要在"决定换源"这个场景里测，站点目录没有这个决策点，放上去只是装饰；其三，我们的数据里只有 9 个站点，其中只有清华发布了机器可读的状态文件，同步状态列在目录里会是"一行有、八行没有"，不如不放。生态与仓库清单的去处在生态文档（那里是换源决策真正发生的地方）。

**仓库清单（该站点镜像了哪些仓库）延后。** 这是"逐站适配"的下一步：站点自己发布的上游文件是唯一可靠来源，实测只有 tunasync 类站点（清华、北外）有 `tunasync.json` + `options.json`，其余站点没有可核实的清单接口。而且这些文件**不带 CORS 头**（实测清华与北外都是 200 但无 `Access-Control-Allow-Origin`），浏览器读不到，必须由后端抓取并缓存后再给前端。做的时候按这个顺序：数据里给镜像加可选 `inventory` 块 → 后端复用现有上游抓取与快照机制 → `GET /api/sites/:id/inventory` → 详情页渲染表格（名称、说明、大小、上游地址）。

**性质标签统一到一处。** `MIRROR_KIND_LABELS`（`apps/web/src/lib/mirrorKind.ts`）是唯一映射，生态文档的来源列表与站点页共用；样式沿用既有的 `.kind`（印章式小方框，不是胶囊）。

## 界面按「仪表 + 尺子」重做：固定刻度轴、首页只列最快 3 个、同步状态不上面

**日期：** 2026-09-21
**状态：** 已实施

这一轮是视觉与信息结构的重做（设计草案在 Superdesign canvas 上迭代，落地在 `apps/web/src/styles/` 与页面组件）。四条结构决定值得单独记下来。

**1. 刻度轴固定在 0–300 ms，分档阈值另算。** 之前每行的读数条按各自的延迟分画长度（`1 - 耗时/1500`），因此每行是一把独立的尺：19 ms 的条和 138 ms 的条看起来都不长，看不出"差多少"。现在所有来源画在同一把固定轴上（`lib/readout.ts` 的 `READOUT_AXIS_MAX_MS = 300`，每 50 ms 一根细线，超出的刻度封顶），行与行、两次测速之间都能直接比长短。分档词（快 / 一般 / 偏慢）仍由延迟分推出：它与推荐评分同源，回答的是"这个来源值不值得推荐"，与"在尺子上有多长"是两件事，所以两者用不同的换算，并分别有测试。

**2. 首页只列最快 3 个。** 来源加多以后这一屏不能跟着变长；第 4 名之后只计数（"已测 5 个来源，这里是最快的 3 个"），要看全部去站点页。测速仍只在用户点击后发生（未测速是默认态）——把默认改成自动测速需要同时改三处承诺（`docs/acceptance-checklist.md` 第 3 项、首页文案、帮助的"不在你打开页面时偷跑请求"），等测速策略定下来一起改。

**3. 首页不显示同步状态。** 同步状态是按生态分开的（同一站点在不同生态上是不同的上游作业，`recordFor(mirrorId, ecosystemId)`），而首页还不知道用户要配哪个生态，挑一条显示等于误导——这与"站点页不放同步状态"是同一条理由。首页因此完全不请求 `/api/mirrors`。

**4. 三种配置方式仍一次全部列出，不做选项卡。** 设计草案里做成了「瞬态执行 / 持久写入 / 配置文件」的选项卡，落地时保留"全部列出"的既有做法：选项卡会把另外两种做法藏起来，而用户往往不清楚自己该选哪一种（"临时装一个包"和"改系统配置文件"的区别不在名字上）。编号按实际存在的方式生成，少了哪一种也不出现空位。

**其它落地项。** 页面外壳的导航宽度 208px → **172px**（`--nav-width`），页内目录栏仍是 208px（`--rail-width`）；首页第一视觉改成"本轮最快的来源"的大号等宽数字 + 来源名 + 推荐标记，搜索框降为普通控件（点一下把它拉到视觉中心、收起测速区与右列）；排名表在 ≤767px 拆成三行且不再显示刻度数字（用户确认：移动端每行右侧已有精确值，尺子只需要"大概多快"，所以整行隐掉而不是只留 0/150/300）；首页里那句"换成推荐来源后，配置文件里会改这一行"的说明删除，只留文件路径与"看完整配置"。

**字体不改。** 设计草案用 Instrument Sans（CDN），本项目字体必须自托管（`docs/decisions.md` 的字体决定），因此沿用 IBM Plex Sans / Plex Mono——大号等宽数字与 `tabular-nums` 才是这套设计的骨架。

## 测速改成“打开就测 + 3 小时本地缓存 + 失败不覆盖”

**日期：** 2026-09-21
**状态：** 已实施

**策略（用户定的四条）。** 打开页面自动测速，尽量不让人看到「未测速」；结果只存本地；3 小时过期，换网络才重测；手动测速只留在生态文档页（首页不放，因为来源变多时一次重测会同时打出很多请求）。加上一条实现约束：**失败不覆盖已有结果**。

**实现落点。**

- 缓存 TTL 15 分钟 → **3 小时**（`PROBE_CACHE_TTL_MS`）。这不是产品参数而是"别过度打扰镜像站"的约束：耗时的变化主要来自用户这一侧的链路，同一网络下反复测既没有新信息，又是对第三方的无谓请求。
- 缓存条目结构改成"最近一次成功 + 最近一次尝试"两段（`lib/probeCache.ts`，版本号 1 → 2，旧数据整体作废）。成功段带**网络指纹**与过期时刻；尝试段记录状态与时间。失败只更新尝试段，成功段保留——这就是"失败不覆盖"的落点，同一个结构还顺手提供了失败冷却：失败后 10 分钟内不再自动重试该来源（`PROBE_FAILURE_RETRY_MS`），手动刷新不受限制。
- 决定"要不要测"集中在一个纯函数 `selectCachedResults()`：签名不一致 → 丢弃；两侧指纹都已知且不同 → 丢弃（换了网络，旧数字不代表当前链路）；未过期 → `fresh`（零请求）；过期但最近失败过 → `throttled`；其余 → `measure`。`useMirrorProbes` 只负责把 `measure` 的那些交给调度器，因此"3 小时内不重复测"是可测的纯逻辑，不是散在组件里的判断。
- **先问指纹再决定测谁**：首页与生态页进入时都先调一次 `/api/net-fingerprint`（同源、本机后端），拿到指纹后再 `revalidate()`。多花一次本机请求，换来的是"跨会话换网"能被识别——否则缓存里没有指纹，只能等 3 小时自然过期。指纹不可用时（静态部署、接口挂掉）退化为只按时间过期，不假装网络没变。
- 首页去掉手动测速按钮，只在**异常态**给「重试」：离线，或本轮全部失败（否则页面会卡在"没有数字"且没有出口）。「未测速」文案因此降级为兜底态，正常路径是 测速中 → 有数据。

**为什么不做省流量（`Save-Data`）分支。** 实测各站探针资源的体积：清华 `robots.txt` 4.0 kB、pypi `robots.txt` 325 B、阿里云 `robots.txt` 295 B、npmmirror `-/ping` 38 B、npm `-/ping` 2 B、腾讯 `-/ping` 3 B。首页 4 个来源 × 3 次 ≈ 20 kB（含响应头），且只发生在首次或过期后；对照本站自己加载的字体就有 75 kB。加一条省流量分支会多一条测试路径，换来的是"这些用户看不到数字"，不划算。真正需要尊重的信号是离线（`navigator.onLine === false`）：那时一个请求都不发。

**已知边界（用户已确认接受）。** 网络指纹是**服务端按出口 IP 网段**算的，因此同一出口下换 Wi-Fi、或开关一个不改出口的代理，检测不到，只能等 3 小时自然过期。抓不到的还有 SSID / 网关 / DNS / 代理设置——浏览器不暴露这些，`navigator.connection` 也只有 Chromium 有（`docs/decisions.md` 的口径条目）。

**连带改掉的承诺。** 「不在你打开页面时偷跑请求」这句话不再成立，三处同步改写：`apps/web/src/help/documents.ts`（改成"会做什么 / 不会做什么"两栏，并新增「什么时候会测速」一节）、首页页脚口径行、`docs/acceptance-checklist.md` 第 3、4 项与关键回归点。
