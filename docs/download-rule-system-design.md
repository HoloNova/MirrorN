# 下载采集规则：存储、判断、清洗与积累设计

## 1. 目标与边界

后台动态取得镜像站文件元数据，识别可安装资源，存入 SQLite；用户搜索、筛选、分页只查数据库。下载文件仍由镜像站提供，测速不变、教程占位。当前仅北大启用，不下载包体，不保存完整目录正文，不恢复百万级依赖库采集。

采集对象按用途区分：软件安装器、预编译运行包、系统安装镜像。具体软件的 DEB/RPM 可以审核接入；开放格式不等于开放整库扫描。源码、文档、校验、调试、数据集和辅助工具不能混作普通安装包；辅助工具若有独立安装用途，应登记为独立软件，例如 Rtools，而不是永远按“辅助”排除。

新手友好不由后缀单独决定：ISO 需要安装介质或虚拟机，Java 运行包需要 Java，网络安装器还会下载组件。规则保存准确用途及必要前置条件，不冒充一键运行或完整离线包。

**规则与实际文件分离：人工维护身份、入口和用途规律；版本、文件名、大小、实际链接由后台产生。静态样本只用来验证规则，绝不作为生产文件清单导入。**

## 2. 改造前的实现与缺口

- `apps/server/src/indexing/software.ts` 只固定登记四个软件身份。
- `indexing/installers.ts` 同时负责目录读取、下钻、正则识别、软件归属、调度和入库；`InstallerFamily` 是硬编码分支，没有独立配置模板系统。
- `db/catalog.ts` 没使用已传入的生态分类与站点资源关系；把软件当生态，有下载才出现。
- `catalog_downloads` 当前只有单个 `platform` 和 `format`，没有用途、变体、规则来源，多系统的 `any` 容易错误映射。
- 当前数据库已有 URL 去重、短整数外键、暂存/事务更新、防旧任务和范围修订号。这些机制保留，不重新复制批次数据。
- 当前 `index.ts:34–48` 将身份配置加载与数据库初始化放在同一异常分支，加载失败会导致资源接口 503。新版规则初始化不能把原本可读的旧下载数据一并关闭。

上述条目描述改造前的问题；以下章节保留设计约束。已实现的路径及验证证据见第 11 节；设计中的未来扩展不因此视作已经接入。

## 3. 存在哪里：配置随源码，结果在 SQLite

### 3.1 规则配置与执行代码

建议布局：

```text
data/download-rules/
  manifest.json           # 格式版本、启用的软件规则与站点绑定引用
  templates.json          # 常见发布布局的默认配置
  software/*.json         # 每个软件的用途与命名特性
  sites/pku.json          # 北大仓库/入口与软件规则的绑定
apps/server/src/indexing/rules/
  load.ts                 # 读取、交叉校验、展开配置、计算版本标识
  templates.ts            # 固定模板执行器
  classify.ts             # 明确的判断流水线
  normalize.ts            # 字段清洗、版本与平台归一化
  parsers/*.ts            # 配置无法清楚描述的少量特殊解析器
packages/shared/src/
  downloadRules.ts        # 与现有数据校验共用的 Zod schema
```

身份仍以现有站点/生态数据为主，软件规则只引用身份 ID，不再复制一份相同的站点或生态字典。对现有不合理的生态 ID 提交明确映射方案，不能按文件名自动合并生态。

配置使用 JSON，方便人工与 Agent 提交；保留现有 Zod 校验，不增加 ORM、远程规则服务或通用规则引擎。执行代码是受控 TypeScript。JSON 可声明锚定的正则和命名捕获组，但不能携带可执行 JavaScript、任意模块地址或脚本。

### 3.2 不开放接口、不热更新

规则不进可编辑的数据库表，不提供 POST/PUT 管理接口，不监听配置文件变更，不从远程下载规则。修改流程为：改配置/解析器 → 校验与回归 → 审核 → 打包发布 → 采集线程重启加载一次。

现有运行目录准备脚本会复制 `data/`，新版规则随同一 API/worker 发布产物携带，不能单独覆盖生产文件“假热更”。查询不等待新一轮采集，继续读 SQLite 的有效数据。

规则版本标识由规范化配置摘要与程序构建标识共同组成：配置不变但解析代码改变，也属于新规则版本。任务和运行记录携带此标识，便于解释“这个结果由哪版规则得到”。不用人工为每个实际文件维护版本号。

### 3.3 SQLite 的职责

SQLite 保存站点、生态、软件、软件版本、有效下载、采集范围/运行日志、少量待核对样本。规则正文仍只在仓库中，不同时保存两套可编辑规则。

需要的关系是：站点支持生态；软件归属生态；软件版本拥有不同站点的下载。站点支持关系不依赖文件数量，不再因为暂未采到下载就消失。扩展现有软件表的生态关联，补小规模站点—生态关系，保留现有下载关联和整数外键。

下载记录拟补充：`purpose`（安装器/运行包/系统镜像）、`variant`（desktop/server/netinst 等）、`platforms`（适用系统列表）、发布状态、版本来源、规则 ID/版本标识。少量元数据可使用受校验的 JSON 列，筛选字段按实际查询需求建列；不把整个源目录响应放进记录。

`platforms` 用三系统枚举列表表达，不为同一 URL 的两个系统复制文件。Unix 安装器可以是 `[linux, macos]`，不能用 `any` 把它送到 Windows。系统 ISO 表示目标安装系统；在 Windows 上制作 Linux 启动盘不意味着 ISO 是 Windows 软件。

## 4. 规则如何组合

### 4.1 通用部分：所有软件共用

目录与文件条目解析；安全的相对路径处理；限速/超时/防循环；元数据完整性；格式提取；平台/架构常见别名；明确非安装用途的识别；URL 去重、事务更新和日志。格式先识别，最终是否接收仍取决于用途证据。

后缀采用最长匹配：`.pkg.tar.zst` 不能误作 macOS `.pkg`，`.tar.gz.sha256` 不是 `.tar.gz` 下载，`.iso.torrent` 也不是 ISO。文件名保留大小写和原始内容；清洗后的匹配字符串不能替换真实 URL 路径。

### 4.2 可复用模板：按发布布局，不按生态硬套

首批模板：

| 模板             | 负责的共性                                  | 不负责的事                                   |
| ---------------- | ------------------------------------------- | -------------------------------------------- |
| 平铺安装包       | 一个目录内提取版本/平台/架构                | 不认所有 EXE 都是当前软件                    |
| 版本目录发布     | 动态发现版本，继承目录版本上下文            | 不把所有版本目录里的压缩包都当运行包         |
| 系统安装镜像     | 版本/架构/介质变体与 ISO 等格式             | 不自动把固件、debug 或救援镜像当普通安装入口 |
| 已审核软件包子集 | 在限定的软件发布目录/小索引里匹配具体包身份 | 不扫描发行版全部依赖库                       |

目录发现与文件用途判断分开。目录发现受审核根与布局限制；文件识别失败不能倒推整个生态不存在。遇到未适配的新目录结构记录原因，不自动全站遍历，也不默默当作完整采集。

### 4.3 软件特性：少量、明确、不能绕过基础约束

软件规则包含软件 ID、生态 ID、模板引用、用途、版本/平台/架构解析、接受条件、拒绝条件、别名策略和证据引用。站点绑定另存仓库 ID、元数据适配器、入口路径和软件规则引用；初期元数据适配器只接北大 `/files/` JSON。

例如：

- Tomcat：版本目录＋审核的 `bin/` 上下文；接受安装器与完整运行包，拒绝 fulldocs/deployer/source。
- Kafka：`kafka_<Scala版本>-<软件版本>.tgz`；两种版本分开，排除 src/site-docs。
- MacTeX：平铺目录、PKG 和日期发布版本；完整包与 BasicTeX 分属软件身份，别名另识别。
- TeX Live：读取同目录年度标记，区分网络安装器、ISO 辅助安装器、升级器，不下钻依赖归档。

规则采用显式字段组合，不使用任意深层覆盖。基础路径和完整更新约束不可覆盖；模板默认值展开后再用允许字段补软件特性；接受项和拒绝项明确列出来源。接受条件不能覆盖已确认的源码/文档等非安装用途。若“工具”本身就是软件，则修改身份/用途规则，而不是关闭全部排除条件。

不做“第一条正则命中就赢”。多个匹配得到完全相同的结果可以合并；版本、身份或用途冲突则记 `ambiguous_rule`，留待核对。同一文件命中两个软件也不能随意归属。

### 4.4 规则配置示意

以下是研究结果可参考的表达，不是当前已实现 schema：

```json
{
  "id": "mactex-main",
  "softwareId": "mactex",
  "ecosystemId": "texlive-ctan",
  "templateId": "flat-installer",
  "status": "draft",
  "purpose": "installer",
  "formats": ["pkg"],
  "matches": [
    {
      "id": "dated-pkg",
      "pattern": "^mactex-(?<releaseDate>\\d{8})\\.(?<format>pkg)$",
      "fields": {
        "version": { "capture": "releaseDate", "kind": "date" },
        "platforms": ["macos"],
        "arch": "unknown"
      }
    }
  ],
  "evidenceRefs": ["pku-mactex-listing"]
}
```

对应站点绑定仅写 `siteId=pku`、`repoId=ctan`、`entryPath=ctan/systems/mac/mactex/`、`ruleId=mactex-main`。不登记当前日期版本或 PKG 下载 URL。样本中的实际文件名进入验证资料，不进入运行清单。

`draft` 不执行，`active` 经审核才执行，`disabled` 不发新任务但不自动清空已有下载。启用/禁用也是源码修改与发布，不是管理接口操作。

## 5. 判断流水线与明确结果

```text
任务绑定审核入口和规则版本
  → 读取完整目录元数据
  → 验证条目与路径、识别格式
  → 区分子目录发现与文件判断
  → 判断软件归属、用途和明确排除项
  → 用官方元数据/目录上下文/命名捕获提取字段
  → 清洗并检查字段冲突
  → accepted / rejected / pending
  → 范围完整性校验、暂存与事务更新
```

证据次序：明确且已适配的官方元数据优先，其次审核的发布目录上下文，再其次软件专属命名规律。不存在相应元数据时不能假装已有。路径与文件名也可能冲突，例如 source 路径里出现 bin 字样；冲突时待核对，不用一个分数或宽泛后缀凑“可信”。

- `accepted`：确认是目标安装资源，身份和必要字段成立，生成数据库下载条目。
- `rejected`：确认不属于普通安装资源；记录原因统计，通常不逐文件长期保存。
- `pending`：软件/用途/版本不明或证据冲突；不展示为可下载，保留有限样本。

目录任务另外记录：已检查、部分识别、正常无候选、待核对布局、采集失败。网络/格式异常走队列重试；正常无候选不包装成网络故障反复重试。上述运行状态不能直接替代“允许删除旧数据”的完整性判断。

正则是提取工具，不是完整决策器。复杂规则无法清楚声明时使用少量命名解析函数，例如 Kafka 的复合版本，而不是造可执行 DSL 或越来越大的万能正则。

## 6. 清洗与去重的具体规则

| 字段             | 清洗与判断                                                                                                    |
| ---------------- | ------------------------------------------------------------------------------------------------------------- |
| 软件/生态身份    | 使用已审核 ID 和关联；不能从模糊关键词自动合并                                                                |
| 文件名与 URL     | 原名保留，逐路径段正确编码；不改路径大小写、不把目录接口当直链；同站点审核根内才能入库                        |
| 格式             | 最长后缀识别并归一化；格式允许不代表用途允许                                                                  |
| 软件版本         | 保留原值与归一值；Node 的 `v` 可归一，Kafka 的 Scala 版本不混入软件版本；不截掉发行包修订号                   |
| `latest/current` | 是镜像别名，不是官方软件版本；能通过已验证元数据/同目录标记解析才关联真实版本，否则明确标记为别名，不伪造版本 |
| 版本排序         | 使用对应规则的语义版本/日期/系统发行版排序；不一律字典序、不比较不同软件的版本                                |
| 系统与架构       | 按用途证据映射；`amd64/x86_64 → x64`、`aarch64 → arm64`；未知仍是未知，不猜用户设备架构                       |
| 变体             | 保留 desktop/server/minimal/netinst/运行时等差别，不因软件版本相同覆盖掉不同安装用途                          |
| 大小/校验        | 未提供就空值，不冒充 0 或已校验；只读元数据，不为补大小下载包体                                               |
| 前置条件         | 只记录已确认的 Java/Perl/网络安装等条件；不自动计算并打包全部依赖                                             |

软件版本按软件身份去重；同 URL 原位更新。不同镜像站 URL 分别保留，不因文件名相同删掉备用站点。不同 URL 不仅凭大小相同认定同一包；确认的 latest 别名可以关联具体发布，不能把文件大小当二进制一致性证据。

## 7. 更新与清理：识别变化不是文件消失

保留暂存、完整成功后范围事务更新、失败清暂存保旧。候选处理与有效下载分离。

三种变化分别处理：

1. 源站完整清单确认文件不再存在：成功校验对应范围后撤销。
2. 新规则明确判定旧记录是源码/文档等范围外条目：发布前报告差异，完整复核后清理，不能藏在普通“未命中”里。
3. 源站仍列出旧文件，但新规则无法识别或证据冲突：保留旧有效快照，记录待核对，不以零识别删除旧记录。

新未知文件不一定阻止其它独立范围更新；但涉及已有有效条目或目录边界的未知项，应阻止受影响范围的替换。没有消失的旧子目录，只是被新下钻规则漏选，不能按“源站撤销”删除。清理依据完整源清单及明确判断，不仅依据筛选后的孩子列表。

现有“数量突降超过一半”守卫继续作为异常拦截，不替代上述判断。规则切换产生大量预期排除时需要单独审阅差异，不能为让它通过直接取消守卫。

更新规则后旧 BullMQ 待办携带的规则版本若不匹配，退出并记录过期，不用新规则执行旧范围清理；由启动强制刷新产生新待办。每轮绑定同一版规则，不半轮新、半轮旧。停用入口不等于立刻删旧数据；源消失、主动退役和规则暂未适配分别处理。

抓取数据不备份，不保留整套旧批次；规则和样本由 Git 维护。发布回退规则不会自动恢复已经删掉的抓取数据，后台按回退规则重新生成，不能把源码回退宣称为数据回滚。

## 8. 如何积累，而不是扩大未知文件库存

只对未知布局、疑似安装用途、字段冲突积累候选，不为每个 checksum/docs 都建记录。候选建议使用一个小 SQLite 表：

`site_id / source_key / reason / signature / samples / observations / first_seen / last_seen / last_ruleset_version`。

相同入口、原因和结构相似的名字归一组，数字替换仅用于候选聚合，不能自动生成生产接受正则。`observations` 表示见到次数，不冒充不同包的数量。

初始容量建议：每入口最多 100 组、每组最多 3 个有限长度样本、全局最多 2,000 组、最长保留 30 天。超限仍累计统计并标明样本不完整，不让样本库变成第二套全量文件表。已解决或过期候选定期清理；失败暂存立即清理；运行日志沿用当前 7 天清理。

不开放管理界面或接口。维护者通过本地只读导出工具取得候选报告，Agent 可以据此提出规则；自动抓到候选不自动激活规则，也不调用运行时大模型去猜用途。

积累流程：

1. 查看逐仓库覆盖报告：实际安装文件、未接入口、规则漏识别、范围外及未核实原因分别列出。
2. 人工/外部 Agent 研究原始样本与官方用途，提出草案。
3. 优先完善可复用模板；只有无法共用时才补软件特性。
4. 给新规则配正样本、相似负样本和字段期望；注明来源、日期和本轮是否实测。
5. 主会话核对证据、差异和影响范围，合并配置/解析器。
6. 校验、定向回归、发布后后台重新采集；查看候选是否下降，不能只看有效文件数增长。

## 9. 校验与发布关卡

使用现有 Zod 校验格式、ID 引用、站点启用边界、模板/解析器名称、允许字段、平台列表、格式及捕获字段。捕获组名称必须与字段映射对应，正则在启动前编译；不接受静态实际文件版本清单或脚本字段。身份同步与规则执行结果不能相互覆盖。

构建时校验一次，采集线程启动再校验。规则缺失/损坏：拒绝启用新采集，但只读连接继续提供旧有效数据；数据库自身不可读才使查询不可用。不要沿用当前配置出错就一起关闭资源库的初始化方式。

验证以真实命名样本和有意义的非 UI 回归为主：正负分类、冲突、复合版本、目录上下文、平台准确性、规则过期待办、旧数据误删保护、生态/软件/站点查询、候选去重与容量。对修改的共用模板重跑其引用软件的样本，不盲目全量编译/全网重爬。

规则产物需包含配置与执行代码的共同版本，部署前检查完整性。沿用现有静态发布/API部署方式，不引入新规则服务。人工 UI 验收仍由用户完成。
