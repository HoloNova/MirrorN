## 2. 关键回归点（最容易碰坏的地方）

**测速的两次可比性。** 首页或生态页连续点两次「测量」，第二次不应再比第一次明显更低——每个来源连续测 3 次、取最快两次的平均，第一次不再是含建连开销的冷启动。某个来源连续两次超时后才显示「超时」，不会白等三倍超时预算；读数条刻度、分档词（快 / 一般 / 偏慢）与推荐来源随之更新。

**改动对照卡。** `/#/ecosystems/apt` 与 `/#/ecosystems/docker-ce` 的「配置文件」下方有「官方默认 → 镜像配置」对照：无符号的行不会变，安全更新行**不在**变化列表里；22.04 会分开计数生效配置与注释里的示例地址；切回官方来源时卡片消失；pip / npm / dockerhub **不显示**这张卡。

**命令生成。** 切换系统、终端、发行版版本、来源之后，第 02 节的命令与配置文件内容必须一起改写，且不能出现跨系统混用（例如 Windows 版式下出现 Linux 的 `sudo` 命令）。apt 选 `24.04` 是 deb822（`/etc/apt/sources.list.d/ubuntu.sources`，`Types:`/`URIs:`/`Suites:`），选 `22.04` 是一行式 `/etc/apt/sources.list`；两种情况 `-security` 都指向官方 `security.ubuntu.com`。

**推荐逻辑。** 最快且同步状态未被阻塞的来源带「推荐」标记并被默认选中；手动点过任一来源后，后续测量不得替换它；同步失败（或暂停）的来源不得被自动推荐，但仍可手动选择。

**同步状态。** `/api` 不可用时显示「同步状态未知」，页面完整可用、控制台无报错；数据可能过期时明确标注；界面显示的同步状态必须与推荐结果一致（不能出现"写着同步失败却仍被推荐"）。站点页只在声明了作业映射的生态上显示同步状态，其余站点不显示——不是显示「未知」，而是本来就没有这个映射。

**主题三处一致。** `apps/web/src/lib/theme.ts` 的注册表、`apps/web/src/styles/themes/*.css` 的 `[data-theme=…]` 选择器、`apps/web/index.html` 首屏脚本里的主题白名单必须一一对应。这条没有自动测试守着，加主题或改配色后必须人工核对第 1 项。

**测速时机与缓存（本轮改动，最容易碰坏）。** 打开首页或生态文档都会自动测速；3 小时内且网络未变时**一个第三方请求都不发**（用 DevTools 网络面板核对：第二次打开页面应为 0 个第三方请求）；把系统时间或等待超过 3 小时后再打开，会重新测；每个来源各自记时间，因此只补测该补的那几个。测速失败的来源**保留上一次成功的结果**（悬停提示「最近一次测速没有成功，上面是上一次成功的结果」），10 分钟内不再自动重试它；连续失败且从来没有成功过时，行内显示「超时 / 失败」。首页没有测速按钮，生态文档页右上角的「测速」是手动重测入口（点它才绕过缓存）。**首页与生态页都不应出现「未测速」以外的异常空白**：没有数字时要么是「测速中」，要么是异常态的「重试」。

**测速口径。**1500 ms 内没有响应记为「超时」而不是失败；no-cors 的来源要说明「响应完成，内容未验证」，不能读成"仓库正常"；全站不出现 `RTT`、`延迟`、`下载速度`、百分比同步进度这类与口径冲突的说法。

**刻度轴的两种换算。** 刻度长度是"耗时在 0–300 ms 固定轴上的位置"（每 50 ms 一根线、超出封顶），分档词（快 / 一般 / 偏慢）来自延迟分 `1 - 耗时/1500`（≥0.75 快、≥0.5 一般）。因此偶然会出现"刻度到顶但写着一般"这类组合——这是设计如此（两个问题不同），但**不能**出现"刻度极短却写着快"。未测到的来源一律画剖面线 + `—`，绝不以 0 长度出现在尺子上。

**首页与站点页的同步状态。** 首页与站点页**不显示**同步状态（它是按生态分的作业，这两页不知道用户要配哪个生态）；生态文档的来源表才显示，且必须与推荐结果一致（不能"写着同步失败却仍被推荐"）。
