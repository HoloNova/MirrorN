# 后台定时采集与数据库文件索引：实施计划

状态：主体、深化设计与BullMQ/Redis选型均已获用户确认，当前已本地实现，验证收尾中；尚未部署、未提交。适用范围：当前只启用北京大学开源镜像站的功能链路；不改测速、不做 UI 重设计、不扩写教程、不扩展其它站点。

## 目标与约束

唯一链路：后台定时采集源站元数据 → 解析实际安装包/依赖文件 → 暂存与校验 → 发布数据库快照 → 查询 API → 前端。

文件清单完全由后台动态采集生成，不维护静态文件表，不把旧目录缓存搬运成新文件索引。每次后端启动都立即执行一轮采集，不论数据库结果是否过期；此后定时更新。所有数据查询均读取数据库，不触发源站请求，包括缓存失效、搜索未命中、选择版本和首次进入页面。目录结构只可用于后台采集，不作为产品数据供用户浏览。点击下载使用数据库中保存的源站文件直链；不托管或代理文件字节。教程只保留关联及占位能力，本轮不写正文。

人工审核的站点身份、生态映射和采集配置可以继续在版本化文件中维护，但运行时查询从数据库读取；动态源站结果不能再作为前端静态索引。测速相关模块及网络指纹不在本轮改造范围。

## 现状证据

- `apps/server/src/app.ts` 的 `browse/package` 路由调用 `crawl/onDemand.ts`，会由用户请求触发源站访问。
- `crawl/siteFiles.ts` 的定时任务只覆盖 installer/iso/files/dataset，大型发行版、语言包仓库不在批量采集范围。
- 现有文件表缺少包名、发行版、组件、发布范围等字段；查询文件不分页，也不能按软件包名检索。
- 现有定时采集保留网络失败前的旧数据，但目录数量截断后仍可能删除整个 resource 的旧文件再写入部分结果。不能用这一实现承诺完整覆盖或无损更新。
- 当前调度在启动和每 6 小时运行；任务避免重入，但没有可跨轮续跑的采集进度。

## 一、统一数据契约与安全发布

保留 SQLite，不增加数据库服务。现有站点、生态、资源表沿用身份，文件索引补充包名、软件版本、发行版/分支、组件、架构、系统、格式、大小、下载 URL、上游校验信息（存在时）、采集时间及采集范围。软件版本与发行版分开；身份不明的字段允许为空，不靠文件名强猜。

增加采集范围、任务进度、暂存批次及当前有效批次的记录。范围例如「某 Ubuntu 发行版的某组件/架构」，不把所有 Ubuntu 版本绑成一次全仓库替换。字段和索引以迁移后的共同契约为准，不保留互不相容的两套文件记录。

新批次先写暂存区；对应范围读取完整、解析和引用校验通过后，事务切换有效批次。失败、超时、预算用尽或解析异常不切换；旧有效数据仍可查询。确认新批次发布成功后才清理已被替代的历史数据，不因资源配置临时遗漏而立即删除有效文件。

验收：中途异常、服务重启、部分索引、异常空列表均不造成旧有效文件消失；完整成功的范围可以移除源站已删除的文件，且不影响其它范围。

## 二、后台任务独占源站访问

将源站 HTTP 访问收拢到后台采集模块，API 查询层不引用采集客户端。每次启动都立即重新采集一轮，不以过期时间跳过；此后每 6 小时调度。采集在后台运行，不阻塞查询服务就绪；启动采集期间继续提供数据库的上次有效结果。增加持久化待办/进度、超时、低频请求、重试退避与公平调度；超预算任务续跑，不发布不完整结果。

大索引采用限额流式读取、解压和分批入库；同步 SQLite 写入事务保持短小，避免一次重任务长时间阻塞查询。启动轮次直接重新获取源站目录/索引，不用本地未过期或未变化判断跳过采集。只拉目录/索引元数据，从中判断实际安装包和依赖包并摘取真实链接；不下载大安装器、ISO 或全部包体。

先核对北大 40 个资源的索引协议、现有数据量和更新信号，形成逐资源采集配置及覆盖范围表；未验证的格式不套用同一种递归扫描器。请求预算根据元数据实际大小配置，不能沿用「80 个目录请求」伪装大型仓库全量采集。

验收：任务可恢复、不重入，后台失败不影响查询；搜索和读取 API 不增加源站请求数。

## 三、按协议采集实际文件

按以下顺序迁移，最终逐项报告北大 40 条资源的接入与缺口，不把小样本或有限范围称为全站完整索引。

1. 安装器、ISO、固件与数据文件：后台重新采集源站元数据，判别实际文件并摘取链接，写入新的安全发布链路；不收集静态文件表、不搬运旧缓存。显式记录采集版本/范围，不再按目录排序截断后覆盖整个资源。
2. Ubuntu/Debian 软件包：读取 Release/InRelease 与 Packages 索引，取得包名、版本、架构、Filename、Size 和可用的校验信息，形成 `.deb` 直链。`dists/pool` 只用于定位后台索引，不出现在查询结果的文件夹结构中。先盘点现有发行版和架构，再明确完整采集单元；预算不足应续跑而不是静默丢弃。
3. 其它发行版/语言包/项目归档：依据实际索引协议建立适配器，如 RPM 元数据、pacman 数据库、Python simple 索引等。Python 不再依赖用户输入触发采集；包清单和包版本文件由后台任务发现、调度及入库。没有统一包索引的资源使用后台目录任务队列，去重、防循环，输出仍然是平铺文件。

不预设 40 个资源都可以同成本全量收录。每条记录注明采集范围、有效文件数、最近成功批次和未覆盖原因；不能解析的条目留在后台接入清单，不能向查询端宣称有可用下载。任何收窄发行版、架构或历史版本的产品取舍，先给出实际规模与范围再确认，不暗中决定。

## 四、数据库只读查询接口

提供统一的站点/生态/资源查询与分页文件检索，支持软件包名、文件名、软件版本、发行版、架构、格式等筛选。默认版本与排序遵循对应生态的版本规则，不使用统一的字典序或从文件名挑第一个数字；不加入推荐评分。

下载资格由当前有效文件索引决定，不再由「可以按需 browse」决定。目录缓存不能被冒充为文件索引，不导入旧目录缓存或静态文件表。新的文件索引只能来自后台源站采集；数据库已有有效结果仅用于新一轮成功之前继续服务，不作为重新采集的替代。

移除源站抓取型 browse/package 实现。前端绑定切换前，若保留兼容路由，也只能查询数据库，不允许联网兜底。未入库明确返回空结果/未收录；数据库故障返回服务错误，不能悄悄抓源站补数据。

验收：查询与分页一致、筛选可组合、直链只对应真实文件；禁止网络的测试环境下所有读取接口仍可运行。

## 五、功能接线与上线切换

不改页面视觉、测速和交互设计。本轮只做必要的功能接线：现有前端目录/按需包查询调用退出，读取分页文件 API；不再依赖浏览源站目录。现有页面结构装不下的展示留给下一轮 UI 设计，不为凑界面重新引入按需抓取。

教程只提供占位字段与关联，不新增或修订两篇现有 Markdown 正文。本阶段验收不以教程正文齐全为条件。

数据库结构调整前做 SQLite 一致性备份（含 WAL），这是结构升级与回退保护，不是收集或迁移文件清单。现有下载查询在新一轮后台采集成功之前继续读数据库已有有效结果。新功能接口可先验证，不部署会把前端入口全部变空的中间版本。同步更新现行产品说明，并标记旧的按需方案已被取代。

## 深化设计（已确认）

### A. 数据库与运行方式

沿用 `/var/lib/mirrorn/mirrorn.sqlite`，Node 24 `node:sqlite`；生产实测 Node v24.21.0，目前 artifacts 为 1,831 行。SQLite 使用 WAL、外键约束、锁等待与短事务，数据库文件保留在现有服务允许写入的目录。业务数据继续使用 SQLite，不改为 PostgreSQL。任务队列建议采用 BullMQ 的 Redis 方案，不自行实现完整的数据库任务队列；这会增加 Redis 服务，尚未安装或启用，待选型确认。未来是否换业务数据库依据完整北大索引的实际容量与查询性能，不凭当前小库断言全量一定轻松。

采集、解压、解析和批量写入放入一个后台 worker thread；API 使用单独的只读数据库连接。worker 不是子代理，而是生产服务内部的后台线程；随现有 systemd 服务启动/停止，不增加独立采集服务；若确认 BullMQ 选型，仅额外增加 Redis 队列服务。Node DatabaseSync 为同步 API，把大规模解析/写入和 HTTP 查询分离，避免扫描大索引时卡住用户请求。结构升级在只读 API 连接建立前完成。

数据库职责如下，名称是实施目标，不声称这些表已经存在：

| 表             | 数据来源与职责                                         | 主要字段                                                                                                                    |
| -------------- | ------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------- |
| `sites`        | 审核的站点身份与允许的采集域；API 从库读取             | id、name、homepage、aliases                                                                                                 |
| `ecosystems`   | 统一生态分类，不因为安装器/软件包再造一份 Ubuntu       | id、label、aliases                                                                                                          |
| `resources`    | 后台发现的仓库，叠加审核的生态映射、协议规则与教程占位 | id、site_id、upstream_key、ecosystem_id、collector、source_url、tutorial_ref                                                |
| `crawl_scopes` | 一个可以独立完整更新的采集范围                         | id、resource_id、发行版/渠道/组件/架构、源索引、active_snapshot_id、last_success_at                                         |
| `snapshots`    | 暂存/有效/已替换的批次                                 | id、scope_id、state、started_at、completed_at、file_count、index_digest                                                     |
| `files`        | 仅由采集器输出的具体文件，不保存文件字节               | snapshot_id、package_name、version、filename、url、size、role、platform、arch、format、checksum、compatibility、observed_at |
| `crawl_runs`   | 实际执行结果，仅供后台诊断                             | job_id、开始/结束、结果、请求数、读取字节、错误                                                                             |

`compatibility` 只容纳协议特有属性，例如 Python 标签、Requires-Python、撤回标记、Debian 依赖表达式；通用筛选字段仍是独立列。先保存依赖表达式，不做自动求解和依赖包打包。

`files` 唯一键为 `(snapshot_id, canonical_url, package_name, version, arch)`（同一Julia包体可能对应不同版本或设备，不丢失筛选关联）；同一文件可能属于多个发行版范围，不能仅按文件名去重。协议内软件包名规范化，但保留原始名称和版本。规范化 URL 只消除非下载片段、校验路径，不删除有下载意义的参数。源站提供的哈希与本机实测包体哈希不是一回事，字段/报告必须区分；本阶段不下载全部包体验证。

查询索引围绕有效批次、包名、版本、架构、用途建立。首期支持包名精确匹配和前缀搜索，以及生态/资源别名；不以无约束 `%关键词%` 全表扫描作为大包库的主搜索路径。文件列表默认 50 条、最大 200 条，提供稳定游标；一次翻页绑定所查询的有效批次，避免刷新切换时重复或漏项，旧批次清理需考虑短时翻页保留期。

### B. 安装文件与依赖包的筛选规则

筛选顺序：确定仓库及协议 → 读取协议索引或官方目录 → 确认具体文件 → 分配用途 → 解析属性 → 校验 URL/引用 → 写入暂存批次。不能靠 `.gz`、`.zip` 等扩展名就认为是安装包。

| 内容                                      | 后台取得方式                                      | 保留的实际文件与字段                                                                                          |
| ----------------------------------------- | ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| Node.js、Miniconda 等安装器               | 官方目录与已有产品专用文件命名规则                | 各平台安装器/运行时归档、版本/别名、平台/架构；不把 Node headers 或源码混成运行时安装器                       |
| Ubuntu/Debian/OPNsense 安装镜像           | 版本/架构/介质目录与可用校验清单                  | ISO、可启动磁盘镜像等；torrent、zsync、签名不作为主下载项                                                     |
| Ubuntu/Debian 与同协议软件源              | Release/InRelease 发现范围，Packages 索引提供记录 | Package、Version、Architecture、Filename、Size、哈希；按仓库根解析 Filename 得 `.deb` URL，不遍历 pool 猜包名 |
| RPM 仓库                                  | repomd 指向的 primary 元数据                      | 包名、epoch/version/release、架构、location、大小和哈希；不把 XML 索引当软件包                                |
| pacman 仓库                               | 仓库数据库中的包描述                              | NAME、VERSION、ARCH、FILENAME、大小与哈希，指向实际 `.pkg.tar.*`                                              |
| PyPI                                      | 后台抓包名清单，再排队抓每个 simple 包页          | wheel 和源分发包；解析包名、版本、wheel 标签、Requires-Python、yanked 与 href/hash                            |
| conda/R 等包仓库                          | 对应 repodata/PACKAGES 等索引；端点逐项核实       | 具体包名、版本、平台、构建/兼容信息及文件 URL，不当作 Miniconda 安装器                                        |
| 固件、Apache 项目归档等无统一包索引的资源 | 后台有边界的目录发现队列，去重、防自引用          | 明确的固件包/项目发布包；源码单独标用途，不和二进制安装器混为一类                                             |

主查询分类为安装器、系统镜像、软件包、固件，源码单独归类。数据集、文档、任意脚本与无法判定用途的归档不因为“可下载”就混入安装/依赖包查询；记录发现与排除原因，不能静默把无法识别算成完整成功。Python sdist 是可由安装工具使用的包，与任意源码归档分开处理。

软件包记录不因名字含 lib/dev/doc/debug 就被删除，它们都是可能实际需要的包。不实现“搜索某包后自动补齐所有间接依赖”；这需要发行版环境与包管理器求解，属于另一个功能。

文件身份优先使用协议字段。版本、架构不明时允许空值/unknown，不拿目录名或第一段数字强填。版本比较按生态规则（Node semver、Python PEP 440、Debian/RPM 原生排序）；原始版本保留。`latest/current` 保存为别名，没取得确切版本时不伪装成数字版本。默认最新仅在用户所选用途/平台/架构/发行版等兼容条件内计算，不引入推荐评分；撤回或不兼容文件需独立状态，不能自动当成正常最新。

### C. 文件链接的依据

链接必须来自索引的文件路径或官方目录的明确文件记录，不能拿根目录、文件夹、帮助页当下载 URL；按基址解析相对链接，核对转义、路径和允许的来源主机。拒绝目录循环、父路径跳出、控制字符与任意跨域抓取。

Python 等协议允许文件位于其它主机。已核实的站点 CDN 通过审核的资源级允许域名单接入；不能因为同名就猜 CDN 路径。回到软件官方源的链接单独记录，不冒充该镜像站提供的本地包。只有后台可以进一步解析跳转；用户查询不发 HEAD/GET 做补查。

索引声明文件存在与实测包体可下载不是同一证据。本阶段的主要链接来源是源站公开索引，不为每个软件包下载包体，也不承诺所有旧链接永远有效。

### D. 强制启动采集与定时更新

每次启动：打开库并完成结构升级 → API 提供现有有效数据 → worker 立即刷新北大官方仓库清单、发现协议索引和采集范围 → 所有已接入范围进入本次重新采集队列，不按本地过期时间跳过。

之后每 6 小时请求一个刷新轮次。已有任务未结束时不并发重复执行，持久化待办并合并调度；对失败项独立退避，不能被一个失败资源堵住全部仓库。建议同站并发 1、两次请求间隔 1 秒、单次网络超时 30 秒、失败最多 3 次（含首尝试，初始指数退避 30 秒/60 秒，429 尊重 Retry-After）；这些是初始配置，不是北大全量刷新耗时承诺，实施根据实际吞吐报告调整。

每次启动都重新取得索引正文，不因数据库未过期而沿用旧结果。临时原始索引可用于流式解析，但不是静态文件清单权威来源。读取压缩索引时同时限制网络字节与解压后体积；优先源站提供且可直接支持的压缩格式，缺少支持的格式需补经过审核的解析依赖，不能跳过却报成功。

PyPI 根包清单已有调研约 47.8 MB，不能再沿用旧“禁止后台读取整页、只准用户按包名查询”的规则。新方案是后台流式获取并发现包名，分批调度包页；完整首轮可能跨多个轮次。读取上限、首次耗时、包数和库容量要现场计量，不能许诺每 6 小时扫完全部 PyPI。请求预算只约束速度和进度，不决定删除旧文件或随机丢弃包。未采集的包搜索只返回未收录，绝不即时抓源站。

### E. 发布粒度与保旧数据示例

一个范围是一个完整协议索引，例如某发行版的某组件/架构；对于 PyPI，一个包的 simple 文件页就是独立范围。协议不提供单个原子索引时，由适配器定义清楚的目录发布范围，不能截取前几个目录后称为全量。

以 Ubuntu 某范围为例：用户仍读取批次 A → 后台把新的 Packages 解析为批次 B → 索引下载完整、必要字段和链接校验通过 → 一个事务将 active_snapshot_id 从 A 改为 B → 用户后续请求读取 B。B 写到一半断电或源站超时，则 A 仍有效。其它架构未采完不影响这个范围发布。

同一资源的新文件数异常减少、有效列表突然变空等，先作为异常暂存，不自动覆盖。权威索引能够确认范围真实撤销时才停用范围；单次 404 或缺项不能直接清空。发布后清理被替代批次和失败暂存；保留当前有效数据、待发布批次以及有限回退批次，避免数据库无限堆积。

### F. 模块边界、接口和验证

- `indexing/queue`：封装 BullMQ 的启动入队、定时、重试和限流，不自建另一套队列；不产生 UI 状态词。
- `indexing/adapters`：PKU 目录、apt、rpm、pacman、Python 等采集和协议解析；只输出统一文件记录及覆盖依据。
- `db/snapshots`：暂存、校验、有效批次切换及回收；任何解析器不自行清空在线数据。
- `db/fileQueries`：站点/生态/资源和有效文件查询；不导入网络抓取模块。
- API：资源目录读取，另提供分页文件查询，如 `/api/files?resource=&q=&release=&version=&arch=&role=&cursor=`；读取只查库。原 browse/package 路由删除或仅做数据库查询兼容，前端不得继续得到文件夹树。
- 教程：仅资源关联、占位状态，本阶段不新增正文。

验收重点：全新空库启动会采集；有库但未过期的重启同样采集；查询时禁用网络仍能返回库内文件；采集中旧批次可读；部分读取/解析失败/事务失败不替换；有效批次切换与分页一致；重复文件、通用架构、软件版本与发行版、撤回包不误分类。日志/后台报告给出每个仓库的支持协议、实际采集范围、有效文件数、缺口、读取规模和失败原因，不将这些任务状态塞回用户页面。

依据：Node 24 SQLite 文档确认 DatabaseSync 为同步 API；Debian Repository Format 明确 Packages 的 Filename 为仓库基址相对路径，且提供 Size/哈希；Python Simple Repository API 明确根索引给项目名、项目页的 href 给文件下载地址及兼容/撤回属性。公开文档为 `https://nodejs.org/docs/latest-v24.x/api/sqlite.html`、`https://wiki.debian.org/DebianRepository/Format`、`https://packaging.python.org/en/latest/specifications/simple-repository-api/`；北大协议实例依据 `docs/research/pku-resource-taxonomy.md`，后者的旧 UI/按需建议不再适用。

### G. 开源组件优先与北大单站开关（已确认）

优先组合成熟组件，不自行重造重试、并发队列、HTML/XML 解析和版本比较机制。BullMQ 是完整任务队列，不只是重试函数；当前建议采用 BullMQ 的 Redis 方案。公开文档现有 PostgreSQL 后端，但本项目没有 PostgreSQL，不为队列改业务数据库，也不自写 SQLite BullMQ 后端。

职责分工：BullMQ/Redis 保存待办、执行状态、延迟重试和任务进度；SQLite 保存站点、生态、实际文件、有效快照和采集诊断。不在 SQLite 再增加一张自研队列表，避免两套任务状态。Redis 是额外运行依赖，需要持久化、仅本地访问、noeviction 配置和部署健康检查；尚未安装或启动。Redis 暂不可用时只暂停采集，API 仍可读 SQLite 旧有效结果。

BullMQ 负责定时任务、attempts/backoff、并发和限流；不再叠加 p-retry 造成重试次数相乘。底层每次 HTTP 请求（包括重试）仍须受同一北大请求限流和超时控制，不能把「任务启动限流」误认为任务内多次请求已限流。业务仅定义哪些错误可重试：网络中断、超时、429、临时 5xx；404、结构不匹配等记录失败并保留旧数据，不反复盲重试。

对比备选：p-retry 是重试组件，p-queue 是进程内并发/限流组件，两者可省掉 Redis，但 p-queue 本身不提供持久化待办与重启恢复，需要额外状态管理。考虑用户要求尽量复用成熟组件，当前优先建议 BullMQ；这项基础设施选型须确认后才实施。安装时核对实际发行版本、Node 兼容性、许可证和依赖，锁定版本，不能仅凭在线最新版文档推断所有 API 在选定版本可用。

解析类组件按协议引入，例如 HTML 使用成熟流式解析器、XML 使用成熟 XML 解析器、归档使用现成 tar/解压组件、Node semver 使用现成版本组件。Debian/RPM/Python 版本规则不强行套 semver；对应组件先核对支持规则，必要的协议映射与有效快照发布仍由本项目实现，不另造通用爬虫框架。具体依赖以每个适配器确认的格式选定，不预装一大套暂不用的库。

当前站点白名单固定为 `pku`。入队、目录发现、解析入库、资源/文件查询都检查同一站点启用配置；只在页面隐藏其它站点不算限制生效。其它站点身份及已有记录保留、不删库，但不发起资源采集、不返回可下载资源。现有测速链路不受这项资源开关改造。

队列任务设计为可重复执行：用启动/定时轮次与范围生成任务身份；数据库快照发布具备幂等性，Redis 完成确认失败导致任务再执行也不能清空旧数据、产生重复文件或让更旧批次覆盖新批次。Redis 和 SQLite 不组成分布式事务，先发布有效快照再确认任务，重复处理由快照身份与代次检查解决。

新增验收：Redis 断开时旧数据库查询正常；其它站点不入队、不采集、不提供下载；任务重试/恢复不重复发布；每次启动仍会强制北大刷新，不因队列已有完成记录跳过。

## 本地实现与当前证据（2026-10-01）

- `indexing/` 集中任务、网络请求、协议解析和线程生命周期；BullMQ/Redis负责持久队列、重复调度和退避重试，p-queue只约束任务内部每次HTTP请求，不叠加重试。主进程与采集线程分别打包，包含解析组件和XZ WASM资源；解析/写入不在HTTP请求线程执行。

### 生产大包名清单的派发修正（2026-10-01）

PyPI根索引只后台收集包名/索引入口到 `discovered_projects`；它是动态采集原料，不是静态文件表，不出现在文件API。BullMQ增加每分钟、优先级25的派发任务；按Redis中的名字游标顺序每次取500条，在已有待办达到1000时停止本次派发，不中断根目录收集、不丢名字。游标在成功入队后才前移，走到末尾才回到起点，源目录的启动/六小时刷新不重置它。普通目录/索引任务优先于包页（20），派发任务低于包页。部署时旧海量包任务先保存入口后压缩，不以清队列解决容量问题。
