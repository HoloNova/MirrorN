# 站点与仓库索引：最小数据模型（讨论草案）

**状态：已被“教程 + 直链下载”主线取代（2026-09-28 当日）。** 本文的“抽样仓库地址”部分已不再作为产品内容：用户否决了“给每个仓库找配置入口”的方向，`data/site-repositories.json` 已删除；现在站点侧只维护**官方公布的目录**（`data/site-inventories/<site>.json`），教程页提供具体文件的下载直链。下列仍然有效并可参考：端点角色（官方清单 / 同步状态 / 更新时间 / 调度）必须分开核实、包体去向不能靠推理（例如清华 Cargo 索引在清华而包体回官方）、检查记录必须区分“元数据可取”与“真实包体已取回”、以及“上游成功 ≠ 目录内容是官方最新”。SQLite 与自动检查仍是未实施的设计。

## 为什么不只存“站点 + 生态 + 拉取方法”

站点首页可访问不代表该站的目标仓库能拉取。例如 Go 代理首页可能返回 404，但模块 ZIP 正常；清华 Cargo 索引在清华，crate 包体却来自官方。站点是目录的主体，实际验证与排名的单位是“站点下的具体仓库”。配置命令可按生态复用模板，但某站的配置地址、包体去向及适用版本不能由模板猜出。

服务器从已审核的仓库拉取**小型真实包体**以判断可用性；浏览器仅对当前生态的少量仓库做**小资源响应测速**，不下载包体。现有浏览器测速缓存继续留在用户本机，不上报或写入数据库。服务器检查的网络位置必须随记录保存；海外检查不等于大陆线路验证。

## 三个最小实体

### `site`：一处有明确运营方的站点

| 字段                               | 含义                                                                       |
| ---------------------------------- | -------------------------------------------------------------------------- |
| `id`                               | 稳定 ID；沿用现有 `data/mirrors.json` 的 ID，去重同站别名。                |
| `name`、`operator`、`homepage_url` | 展示名称、运营方与官方主页，防止联盟入口或跨运营方官方源被合并成一个站点。 |
| `evidence_url`、`reviewed_at`      | 官方证据及人工核实日期；没有来源的站点先留在研究资料中。                   |

站点名称/别名等审核后的静态事实由版本化数据维护；站点不存一个代表全部仓库的“可用分数”。目录可汇总仓库已验证数量，但要保留每个仓库的差异。

若要自动读取官方清单，额外登记**已现场验证**的 `site_feed`（`site_id`、`url`、`role`、`format`、`verified_at`）。`role` 区分全站清单、同步状态、更新时间；单仓库 `config.json` 和调度评分接口不能冒充全站清单或同步状态。没有可靠清单的站点仍可人工核对收录；不凭猜测的 URL 启动定时抓取。

### `repository`：站点提供的一条具体配置入口

| 字段                                          | 含义                                                                                                             |
| --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `id`、`site_id`                               | 稳定仓库 ID 与所属站点；同站同生态可以有不止一个入口。                                                           |
| `ecosystem_id`、`protocol`                    | 关联已定义的生态与协议适配器，例如 Go module proxy、Maven、Cargo sparse、apt；不在数据库中存可执行的“拉取脚本”。 |
| `config_url`                                  | 用户工具实际配置的 HTTPS 地址；Cargo 的 `sparse+` 是生成命令时加的协议标记，不属于 HTTP URL 本身。               |
| `artifact_route`                              | 经核实的包体去向：站点自有域名/可归属的 CDN、官方上游、调度跳转或未知；不能仅凭索引 200 推断。                   |
| `applicability`                               | 仅当有证据时记录版本、架构等限制；`unknown` 不等于“全版本支持”。                                                 |
| `browser_probe`                               | **可选**的仓库级小资源 URL、HEAD/GET、CORS/no-cors、是否可加查询参数；不能沿用站点首页探针代替仓库测速。         |
| `check_target`                                | **可选**的已审核代表性小包标识/路径；由生态协议适配器解析实际包体地址，不拼凑 `config_url + 固定后缀`。          |
| `evidence_url`、`reviewed_at`、`review_state` | 官方依据、审核日期及发现/地址核实/配置可用的人工准入阶段。                                                       |

审过的站点和仓库关系须只有**一个权威来源**：现阶段仍由版本库数据维护，再生成查询视图；不能让静态 JSON 与 SQLite 分别人工编辑同一仓库 URL。搜索、站点页与生态页都引用同一仓库 ID。未核实的上游清单条目不得自动升级为可配置或可推荐。

### `repository_check`：服务器一次实际检查的观察记录（SQLite）

| 字段                                                    | 含义                                                                                         |
| ------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `id`、`repository_id`、`checked_at`、`network_location` | 哪个仓库、何时、从哪个网络位置检查；用于判定过期和解释地域差异。                             |
| `kind`                                                  | 元数据检查、真实包体检查必须分开；HEAD/opaque 不算包体取回。                                 |
| `method`、`result`、`http_status`、`duration_ms`        | 实际请求方法、成功/失败/超时、状态码及耗时；不能把响应头的 `Content-Length` 当作下载字节数。 |
| `requested_url`、`final_url`、`redirect_chain`          | 真实请求和跳转路径，可复现检查；仅存“200”或最终域名无法发现误写的仓库路径。                  |
| `bytes_read`、`content_valid`、`error_code`             | 实际读取的字节、协议对应的包体校验结果与失败原因；HEAD 的声明长度不是已读取字节。            |

只有完整包体检查成功、证据仍在有效期内且配置适用时，仓库才进入自动推荐的候选集合；失败或过期应降级为未知/不可推荐，不能由另一站或另一上游的成功续命。有效期和抽样频率尚未确定，需试点观测后决定，不能提前把一个任意时间写成承诺。网站不会存用户的浏览器测速记录，也不在数据库持久化一个会过期的“总分”；生态页基于当前合格仓库与用户本地测速计算排名。

## 拉取方法哪些固定、哪些不能固定

- 固定在代码中的**生态协议适配器**：Go 的 `.info`/`.zip`、Maven 元数据/JAR、Cargo sparse `config.json` 与 `dl`、pip simple 页面链接、npm 包元数据内的 tarball URL；发行版还需要按版本/架构解析索引。配置命令按操作系统与 shell 的模板由现有生成器维护。
- 按仓库审核的**实例参数**：配置基址、适用范围、代表性小包、浏览器探测路径和包体真实归属。Cargo 与 npm 的下载地址可能由上游响应给出，不保证与索引同域；Go 根路径 404 也不等于协议不可用。
- 现有 `/api/mirrors` 的同步状态可保留作附加信息，但不是最小必需字段。当前推荐将同步占 20 分、稳定性固定为 0.5；若新排名改为“实际拉取准入 + 用户侧测速”，需要明确重做评分，不能悄悄沿用旧权重。多源同步若继续使用，还须先修逐源过期问题。

## 存储和首批边界

当前几十条人工审核记录**不因条数而需要数据库**。现在由 `data/mirrors.json` 维护站点身份，`data/site-inventories/<site>.json` 维护官方公布的目录（校验：站点存在、同站唯一、目录入口与站点主页同源、仓库 id/路径唯一），教程页的文件版本来自镜像站目录接口的按需解析。旧换源向导的 `data/ecosystems/*.json` 仍在仓库且仍被数据校验，但已无界面入口。浏览器测速（站点详情的手动“测一下本站响应”）仍只存在用户本机。

若实施自动检查与历史保留，SQLite 仅需优先持久化 `repository_check`；`site`/`repository` 可由版本化、经审核的数据导入为只读查询视图，避免两处人工维护同一事实。若后续自动读取站点清单，再单设“发现但未经审核”的候选记录及来源/最后发现时间，不直接混入上述审核数据。是否让前端通过 API 读取增量目录，需与现有静态 JSON 构建、最后有效快照和公网部署方式一起设计。

**试点结果（已被本轮主线取代）：** 当年只实现静态、经抽样的目录层（28 站、33 条无向导仓库，USTC pip 与华为 npm 加入旧向导）。用户否决该呈现后，`data/site-repositories.json` 已删除，站点详情改为展示官方公布的目录（首个是北大 40 条），抽样数据不再作为产品内容。仍然成立的结论：清华 `tunasync.json` + `options.json`、USTC `index.json`（只有更新时间，不等于同步成功）、腾讯 `source.js`（JS 包裹，不能执行）都无 CORS、必须经后端取回；**给通用状态源加第二个上游前，必须先修掉“所有源共用一个最近成功时间”的过期判断**（北大的按仓库记录实现是正确做法，但它只服务北大）。
