# MirrorN：项目结构与下载链接统一方案（北大试点实施基线）

**状态：已确认的产品/数据规则与问题基线；本轮先以北大试点实施，部署信息另记 `PLAN.md` 第七节。** 依据 2026-09-29 公网 API、`mirrorn-api` 抓取日志和工作区代码。**本阶段只整理项目结构、资源索引和下载链接，不写新教程，也不以是否有教程决定资源能否收录。** 文件由镜像站直接提供；现有 Markdown 教程保留，后续单独整理。

## 已核实的问题

- 公网北大有 40 条资源，**9 条有文件直链、31 条没有**，只有 2 条挂了教程。按类型：25 条发行版软件源 + 5 条语言包仓库被抓取器主动跳过（每条 0 次请求）；Apache 归档被设为不抓。它们仍在首页以“资源”展示，搜索结果中的无教程项还统一标“下载”。`crawl_runs.ok` 对主动跳过也记 true，不能解释为文件可下载。
- `/api/resources/pku:ubuntu-cdimage` 有 2 条 ISO，但 `apps/web/src/lib/downloads.ts` 的 `isArtifact` 要求 `version !== ''`，页面会过滤掉这两条。通用 ISO 的 `platform=any` 又与自动检测得到的 Windows/macOS/Linux 精确匹配冲突，能形成“库里有、下载组件里没有”的另一类空态。
- 同一个概念拆成不同生态 ID：`ubuntu` / `ubuntu-releases`、`debian` / `debian-cd`。同站同生态的“去安装镜像”关联因此可能找不到；用户要找的是 Ubuntu 或 Debian 的**用途**，不是两份生态。
- 前端把 `data/site-resources/pku.json` 编进 JS，首页与搜索用静态数组；API 用同一份数据启动时导入 SQLite，却另算文件数和版本。`/api/resources` 的搜索与首页搜索并非同一实现；前者的 SQLite LIKE、后者的本地子串匹配与排序规则也不一样。当前“只索引有文件的资源”只是 `SearchBar.vue` 注释，实际代码并未过滤。
- 版本解析同时存在服务端的文件名推断、目录优先规则、前端的数字比较和字典序下拉排序，可能造成“库中有文件，选择器显示不出”。现有教程只替换 `{{filename}}` 等少数占位符，不能声称整篇教程已按版本适配；**教程内容的修订不在本阶段范围内**。
- 现有后端启动即抓、以后每 6 小时抓一次；每资源按目录层数与每层目录数截断，整轮默认 80 个目录请求。**没有独立的每资源 8 请求硬限制**：生产日志里 Debian CD 一项用 43 次请求。失败/部分读取时可能清空旧文件，或者把只抓了部分目录当作该资源完整列表。页面仅显示最后一次文件的抓取时间，没有区分完整、局部、失败、过期。北大另有独立的任务状态缓存和旧的镜像状态缓存；这些不是文件直链可用性的证明。

## 单一产品模型

用户入口统一为 **软件/生态 → 想下载什么 → 站点提供的可下载文件**。有现成教程时可在文件选择区下方展示，教程不是本阶段的入库门槛。站点目录是同一批资源的另一种视图，不是第二套下载产品。以 Debian 为例：“安装 Debian”下选镜像站、发行版、架构与 ISO；“安装 Debian 软件包”是另一种用途，需先指明包名，不能把 `/debian/` 仓库根目录充当安装包。以 PyPI 为例，先搜具体包名和版本，再解析镜像站的 simple 元数据/文件链接；“PyPI”本身不是一个可点击下载的文件。

建议的实体边界：

| 记录                | 作用和权威来源                                                                                                   |
| ------------------- | ---------------------------------------------------------------------------------------------------------------- |
| 站点 `site`         | 身份、官方域名、已核实的目录/状态端点；审核后的内容版本化。                                                      |
| 产品/生态 `product` | 用户理解的 Ubuntu、Debian、Node.js、Python 包等；不因 ISO、软件源而复制生态 ID。别名归这里。                     |
| 下载用途 `task`     | 安装系统、获取运行时安装器、获取某个软件包、下载数据集；规定查找直链所需输入（系统、架构、版本、包名或项目名）。 |
| 站点资源 `source`   | 某站给某用途提供的目录入口、上游索引协议、适用范围及抓取策略；可有多个来源，只有一个经审核的配置位置。           |
| 文件 `artifact`     | 源站返回的可下载直链、版本、平台、架构、文件格式/大小、对应目录与观测时间；文件必须归属于一个明确的用途。        |
| 观测 `crawl_run`    | 每个源的尝试时间、成功/局部/失败/跳过、实际请求数、错误、最后完整快照时间；与站点同步任务状态分开。              |

版本化数据保存审核决定与**抓取规则**；SQLite 保存已发现文件、快照与抓取历史；首页、搜索、站点视图、下载页都从**同一后端目录投影/API**读取。现有 Markdown 教程按资源 ID 关联、暂不扩写。后端不可用时应明确是“目录暂不可用”，不能用旧静态索引制造一个看似可下载却无文件的入口。保留旧 URL 的重定向，但不再给无文件的伪下载入口。

## 内容准入与页面规则

1. 首页与搜索的主结果只显示**能交付下载链接**的用途：至少有一个可选的具体文件直链，或已核实的按需索引查询能针对用户指定的包名/版本返回文件。**不要求先有教程。** 暂未接入文件解析的仓库保留在站点“官方目录”资料视图，不标“下载”，也不混进可下载结果。
2. 软件包仓库与安装器不能用同一种抓取器。安装器/ISO 按明确目录计划获取可用版本与文件；PyPI、apt 等海量包仓库先用包名/发行版/架构缩小范围，再按需查询协议索引并缓存有限结果；Apache 多项目归档先选项目，不能递归全站。不能低成本查到真实文件的用途标记“待接入”，不要输出伪直链。数据集按实际项目/文件名查找，不能靠“数据集”大类标题充当下载结果。
3. 统一下载组件状态：有可选文件 → 系统/架构/版本/格式与明确直链；目录部分抓到 → 标注只收录的范围，允许继续按需查；刷新失败但有上次文件 → 标注旧快照并检查链接，不能写“最新”；没有文件 → 不在主搜索显示，站点资料页仍可展示官方目录。`any`/未知平台应独立处理，版本缺失不能无声丢弃；没有版本含义的文件不展示虚构的“最新版本”。
4. 现有 Markdown 教程保留在下载区下方；本阶段不新增、不重写教程内容，不用“有无教程”来决定下载是否显示。无教程的下载页只呈现可核实的文件与选择条件，不能标成“安装教程”；教程按版本适配另立任务。
5. 目录采集与测速分别负责**文件有什么**与**用户到目标站点响应耗时**；抓取任务完成、站点同步状态、单次 HEAD、响应耗时都不能替代具体文件可用。测速仅在用户触发时进行，不用于推荐版本。

## 代码与数据目录的归属

| 位置                                             | 本阶段唯一职责                                                                                                              |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------- |
| `data/mirrors.json`、`data/site-inventories/`    | 人工审核的站点身份、官方目录依据；保留原始目录含“暂不能本站下载”的条目。                                                    |
| `data/site-resources/`                           | 审过的站点目录项 → 产品/用途映射与抓取配置；不保存运行时文件清单。`ecosystem-taxonomy.json` 去重“同产品不同用途”的重复 ID。 |
| `apps/server/src/crawl/`                         | 站点目录适配器、按用途的文件/协议索引解析、定时抓取与请求预算；不能把不同资源都交给一个文件扩展名扫描器。                   |
| `apps/server/src/db/`                            | 目录导入、SQLite 迁移、文件快照与查询；抓取器只写已验证过的目录输出，不负责 UI 文案。                                       |
| `apps/server/src/app.ts`                         | 统一对外的产品、用途、站点资源和文件查询接口；列表与详情同源。                                                              |
| `apps/web/src/lib/`、`apps/web/src/pages/`       | API 结果的类型检查、文件选择和页面展示；不要在前端再打包一份独立的资源查询/排序逻辑。搜索和站点页都消费同一目录视图。       |
| `apps/web/src/tutorials/`、`data/tutorials.json` | 现有 Markdown 和关联声明保留；本阶段不新增正文。                                                                            |

目前项目还留着旧换源向导、推荐、通用状态、探针等代码和 `data/ecosystems/`。本阶段先核查这些模块的**实际运行引用**；仅对已无路由/调用方的旧代码做有证据的清理，保留站点详情仍在使用的手动测速。`MAIN.md` 的立项历史不作为当前模块规范；实施后以本方案确认的目录职责更新当前产品说明，避免旧文档继续指导新功能。

## 北大试点的实施顺序

1. **先消除错误承诺**：修掉空版本/通用平台的文件丢失和下拉空态；首页搜索与站点页区分“有直链或按需文件查询”与“仅收录目录”，取消虚假的“下载”标签与按文件数代表覆盖的数字。保留现有可用的 Miniconda、Node 下载，不先扩大到其余 27 站。
2. **统一产品与用途映射**：把 Ubuntu ISO 与 Ubuntu 软件源、Debian ISO/固件与 Debian 软件源归到同一个产品下的不同用途；整理站点 40 条官方目录，但只有能提供可核实文件入口的用途进入下载搜索。基于一个后端视图服务首页、搜索与资源页，保留现有资源页 URL 和已有 Markdown 内容。
3. **按用途补下载入口**：先修 Ubuntu、Debian 安装镜像的版本/架构与直链；再选一个包仓库（如 PyPI 的指定包）做受限索引查询、解析源站给出的实际文件 URL；Apache 先选项目、再按需列目录，不能把 Apache 根目录当成一个“可安装软件”。其它目录逐项接入；**这一阶段不写新教程**。
4. **统一抓取质量**：每源明确抓取计划和请求预算、避免重入；只有完整且解析有效的结果原子替换文件快照，失败保留上次有效数据并标过期；记录“局部目录/版本范围”，不把截断伪装成全量。把北大旧任务状态、通用同步状态与资源文件状态隔离，删除界面不使用的任务状态呈现。
5. **发布与验收**：针对资源解析/选择与目录状态运行非 UI 检查；后端数据库迁移留备份且可回退；发布到公网后由用户人工检查首页搜索、文件直链、按需查询、空结果、旧数据、手机宽度和深浅主题。项目规范禁止 UI 自动化验收。

本方案只定义产品与数据规则；页面视觉沿用现有主题与自托管字体，不在尚未确定内容结构时重做皮肤。已实现的首批范围是安装器/ISO 定时抓取、北大其他仓库逐目录查询及 PyPI 按包名查询；apt 按包名/架构解析索引、全站其它 27 站的目录适配与教程版本适配仍是后续工作，不能以北大试点冒充全网覆盖。
